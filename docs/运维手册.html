发票易 InvoiceEase · 运维手册

1 日常巡检2 告警处置3 备份与恢复 4 日志5 启动自检6 安全配置7 常见问题

发票易已内置运维兜底子系统：任务执行全程记录、告警企微推送、数据库与原件每日备份、 日志落盘轮转、启动自检。日常运维只需登录 Web 管理后台的「运维」页（/ops）即可完成巡检与处置； 恢复与深度排障在服务器命令行完成。全部运维能力仅系统管理员可见，普通用户访问 /ops 会被自动弹回首页。

1. 日常巡检（Web 后台）

登录后台 → 左侧进入「运维」（仅系统管理员）。页首为状态卡片（版本 / 运行时长 / 数据库体积 / 原件体积 / 磁盘剩余 / 最近备份时间），下方四个 Tab 各看重点：

Tab看什么重点关注
任务班表任务与队列任务的执行记录（触发方式 / 开始时间 / 耗时 / 结果 / 错误列） 异常 与 失败 行——点错误列查看原因；顶栏可手动执行白名单任务
告警告警历史列表（级别 / 规则 / 内容 / 触发时间） 有无 严重 级告警，按第 2 节处置表逐条处理
备份备份文件列表（大小 / 时间）+ 下载 最近备份时间是否距今 24 小时内；必要时「立即备份」
自检深度自检全项（fernet_key / 默认密钥 / 迁移版本 / 磁盘 / 目录可写 / 引擎能力） warn / fail 项——按第 5 节处置；可「刷新自检」「查看日志尾部」
巡检建议：每日上班后花 1 分钟看一遍——任务 Tab 无红色、告警 Tab 无严重、备份 Tab 最近备份为今天、 自检 Tab 无 warn/fail。全部正常即可。

交易性质与发票要求

回单入库即按规则判定交易性质（税费/社保/银行费用/工资/内部调拨/客户回款/财政/补贴/利息收入/采购）。 「是否需要发票」由性质派生，分三档：需取得发票（采购等，进「无票支出」并催票）、 需我方开具（客户回款，销项对账）、无需发票（税费/社保/银行费用等，缴款书或银行凭证即凭证， 不计入「无票支出」也不催票）。

规则升级后，在运维页「手动执行 receipt_classify」回填历史（跳过人工覆盖行）。 不跑则该次升级前的历史回单维持「待定」（按需发票保守处理，继续出现在催票队列里可能被误催）； 任务幂等，首次升级后跑一次即可，重复执行不会改动已人工覆盖的行。 误判可在回单详情改「交易性质」，或选「跟随规则」清除人工覆盖（留痕于审计日志 RECEIPT_CATEGORY）。

2. 告警处置

告警由后台每 5 分钟评估一次规则自动产生，写入「告警」Tab 并推送企微机器人 （同一规则 4 小时内不重复推送）。收到推送后按下表处置：

rule_key含义级别首要动作
task_failed.*某任务近 1 小时失败 ≥3 次（* 为任务名） 严重 运维页「任务」Tab 找到该任务的失败/异常行看错误列，再配合日志尾部定位；修复后「手动执行」验证
mailbox.stalled收取邮箱超过 2 倍轮询间隔未更新，收取通道疑似瘫痪 严重 「设置」页找到对应邮箱点「测试连接」；检查邮箱密码是否过期、服务器是否可达、账号是否被锁
backup.missing超过 26 小时未产生新备份（当日备份失败或未执行） 严重 运维页「备份」Tab「立即备份」手动补一份；再查磁盘剩余与备份目录是否可写
backup.failed近 24 小时内 ops_backup 任务执行失败（执行了但失败，与 backup.missing 并存） 严重 运维页「任务」Tab 过滤 task_name=ops_backup 看 error 列，再查磁盘空间 / 备份目录可写性；修复后「手动执行 ops_backup」补一份备份
disk.low磁盘剩余低于 10% 警告 扩容磁盘或清理旧日志/临时文件，释放空间后自检确认磁盘剩余回升
review.backlog待复核发票积压超过 50 张 警告 进入「待复核」清单催办财务处理积压；属业务健康告警，处理即可
parse.error_rate近 1 小时解析异常率超过 20%（样本 ≥5 张） 警告 运维页「任务」Tab 过滤 task_name=parse，看 error 列样本与日志尾部，定位异常发票原件
冷却与恢复：同一规则触发后 4 小时内不重复推送（防刷屏）；规则恢复正常即自动停止触发， 运维页当前状态可见即闭环，无单独的「恢复推送」。

3. 备份与恢复

备份机制

  • 内容：SQLite 数据库一致性快照 + 发票/回单原件目录，合并为一个 tar.gz（内含 meta 信息：备份时间、数据库迁移版本、关键表计数）。
  • 时机：每天 02:17 自动备份（后台进程需保持运行）；也可在运维页「备份」Tab「立即备份」随时手动备份。
  • 保留：默认保留最近 7 份（INVOICING_OPS_BACKUP_RETENTION 可配），超出自动删除最旧。
  • 位置：INVOICING_OPS_BACKUP_DIR（默认 ./data/backups）。
  • 文件名时间：备份文件名时间戳为 UTC（invoiceease-backup-YYYYMMDD-HHMMSS.tar.gz），与运维页展示的本地时间不同，核对时请注意时区。
保密要求：备份文件等同于数据库，内含发票与账号等敏感数据，需与数据库同等保密—— 建议将 INVOICING_OPS_BACKUP_DIR 指向第二块数据盘或网络盘，防止与系统同盘同时故障。

恢复（服务器命令行）

在 backend 目录下按序执行。恢复会将当前数据库替换为目标备份，必须先停服：

# 1) 停服（先停 uvicorn 与 arq worker）
# 2) 执行恢复（<文件> 换成备份 tar.gz 路径；不加 --yes 只预览不动手）
uv run python scripts/restore_backup.py data/backups/invoiceease-backup-20260917-021700.tar.gz --yes
# 3) 校验数据库迁移版本与代码一致
uv run alembic upgrade head
# 4) 重启服务
uv run uvicorn invoicing.main:app --reload
安全网：恢复执行时会把当前数据库另存为 <db>.pre-restore 后再替换，误恢复可找回。 恢复完成后建议立即做一次「立即备份」产生新基线。

4. 日志

  • 位置：INVOICING_LOG_DIR/invoicing.log（默认 ./logs/invoicing.log），后台、调度器、uvicorn 日志汇入同一文件。
  • 轮转：单文件上限 10MB（INVOICING_LOG_MAX_BYTES），超出滚动保留 9 个历史文件 （INVOICING_LOG_BACKUP_COUNT），无需手工清理。
  • 脱敏：日志自动对消息中的 password / token / secret / key 等敏感键值打码为 ***；请求头不落盘，授权令牌不写入日志。
  • 查看：运维页「自检」Tab「查看日志尾部」实时看最近 200 行，日常排查以此为准； 如需完整日志文件，可在服务器上直接查看 INVOICING_LOG_DIR/invoicing.log， 或经管理员接口 GET /api/v1/ops/logs/download 下载当前日志文件。
  • redis 部署：queue_backend=redis 时，arq worker 进程的日志走 stderr（不汇入 invoicing.log）。排查队列任务失败时，请在 worker 进程自身日志中查看。
级别：日志级别由 INVOICING_LOG_LEVEL 控制（默认 INFO），修改后重启进程生效。
已知问题：macOS 上大日志经下载接口获取可能截断，完整日志以服务器上 INVOICING_LOG_DIR/invoicing.log 直接查看为准。

5. 启动自检

服务每次启动时自动执行一次深度自检，结果同时写入日志、严重项落告警，并可在运维页「自检」Tab随时重跑。 INVOICING_STARTUP_CHECKS_STRICT 默认为 false——自检 warn/fail 项只告警不阻断启动； 设为 true 时密钥类 warn 项升级为阻断（fernet_key / 默认密钥；fail-fast）。 INVOICING_ENV=production 与 strict=true 等效且更强：弱密钥 / 未配置 inbox_dir / 离线模式 + 云端 LLM 一律拒绝启动（见第 6 节）。

检查项级别处置
fernet_key 未配置/非法（非 44 字符 base64） warn（无存量密文时）
fail（库中已有凭据密文）		 生成合法密钥并在 backend/.env 覆盖：
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
将输出填入 INVOICING_FERNET_KEY= 后重启。注意：更换密钥后此前加密的邮箱密码将无法解密，需按下方「Fernet key 配置与轮换」迁移。
jwt_secret / mcp_token / admin_password 仍为默认值 warn（strict / production 下阻断） 在 backend/.env 覆盖全部默认值：INVOICING_JWT_SECRET、INVOICING_MCP_TOKEN、 INVOICING_ADMIN_PASSWORD（勿用 change-me / admin123），重启生效
workbuddy_inbox_dir 未配置 info（dev）
fail（production）		 为空时 MCP 文件级工具可读服务器任意路径；生产必须配置 INVOICING_WORKBUDDY_INBOX_DIR 为专用附件目录
离线部署（offline_deploy）启用了云端 LLM 端点 fail FRD 要求数据不出企业内网：改 INVOICING_LLM_BASE_URL 为内网模型（vLLM/Ollama）或置 INVOICING_LLM_ENABLED=false
存储 / 日志 / 备份目录不可写 fail（默认仅告警，strict=true 时阻断启动） 为三个目录授权写权限（storage_root / log_dir / ops_backup_dir）
数据库迁移版本落后 warn 在 backend 目录执行 uv run alembic upgrade head 后重启
磁盘剩余 < 10% warn 按第 2 节 disk.low 处置（扩容 / 清理）
OCR / LLM 能力状态 info 能力现状展示，非故障，无需处置

Fernet key 配置与轮换（邮箱凭据加密）

邮箱密码 / SMTP 密码 / Agently token 用 INVOICING_FERNET_KEY 加密入库。 密钥未配置或非法时系统拒绝保存凭据（邮箱管理页会提示 400），这是为了防止「保存时成功、重启后密文全体失效」的静默数据损失—— 旧版本在该场景下会退化为进程内临时随机密钥。

  1. 首次配置：生成密钥（上表命令），填入 backend/.env 的 INVOICING_FERNET_KEY，重启后正常录入邮箱。
  2. 更换密钥（轮换）：先停服 → 用旧 key 把存量密文迁移到新 key → 更新 .env → 重启： 
    uv run python scripts/reencrypt_secrets.py --from-key 旧KEY --yes
    不加 --yes 只预览受影响邮箱数。迁移后旧 key 即可废弃。
  3. 旧 key 已遗失：密文无法恢复，只能在邮箱管理页逐个重新录入凭据（自检会以 fail 点名受影响邮箱数）。

6. 安全配置（production 形态）

对外服务部署时置 INVOICING_ENV=production：启动自检按最严口径执行（第 5 节）， 弱配置直接拒绝启动，避免「带着默认密码上线」。

配置项作用生产建议
INVOICING_ENVdev / production；production = 自检升级为阻断production
INVOICING_LOGIN_MAX_FAILURES
INVOICING_LOGIN_LOCKOUT_MINUTES		 登录限流：窗口内连续失败达上限即锁定该 (IP, 用户名)，锁定期内正确密码同样拒绝；429 写审计（含 rate_limited 标记） 默认 5 次 / 15 分钟；如财务室共用出口 IP，可适当放宽
INVOICING_CORS_ORIGINS
INVOICING_ALLOWED_HOSTS		 跨域来源白名单与 Host 头校验；空 = 关闭（同源部署零影响） Web 与 API 同源部署时留空；分开域名时配 CORS，公网入口建议配 ALLOWED_HOSTS
INVOICING_MCP_TOKEN legacy 全局 MCP 令牌，默认关闭（留空）；一旦配置 = 最小 id 管理员全权 保持留空，统一用「令牌管理」页的个人令牌
INVOICING_OFFLINE_DEPLOY 声明数据不出内网：true 时启用云端 LLM 端点将拒绝启动 内网交付置 true 并配内网 LLM，或关闭 LLM

7. 常见问题

Q1：自检提示「迁移落后（db=… head=…）」

数据库版本落后于代码迁移。在 backend 目录执行 uv run alembic upgrade head， 再在运维页「自检」Tab 点「刷新自检」确认恢复 ok。

Q2：邮件解密失败 / 收取报「无法解密邮箱密码」

邮箱密码用 INVOICING_FERNET_KEY 加密存储。若该密钥曾为非法占位值（旧版本会临时随机生成、重启即失效）、或更换过密钥， 历史邮箱密码将无法解密（自检以 fail 点名受影响邮箱数）。处置：仍持有旧 key 时用 scripts/reencrypt_secrets.py --from-key 旧KEY --yes 迁移；旧 key 遗失则在「设置」页对受影响邮箱重新录入凭据。详见第 5 节「Fernet key 配置与轮换」。

Q3：备份为什么没有出现？

每日备份由后台进程内的调度器触发（02:17），进程需保持运行。若进程夜间重启过或长期未运行， 直接运维页「备份」Tab「立即备份」补一份即可。

Q4：如何确认系统仍在正常工作？

三处一键确认：运维页「任务」Tab 看 mailbox_poll 最近记录为 成功、 「告警」Tab 无严重告警、「自检」Tab 全 ok。
