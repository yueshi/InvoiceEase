# 电子发票财务 Agent 中台——设计优化与功能清单（修订版）

日期：2026-09-13 ｜ 状态：建议稿
来源：对《财务/发票数字员工 AI Agent 设计（1 总控 + 多专业 Agent）》的评估，
结合**发票易**已真实落地并踩过的坑（本文所有"实战依据"均为已复现问题）。

## 一、总评：版图完整，但有三个结构性风险

参考设计的功能版图（13 个 Agent、5 条闭环、L0–L3 分级）**方向正确**，
主线"先抓 电子发票采集 + 验真查重 + 报销入账"也与我们一致。以下三点建议修订。

### 风险 1：「13 个 Agent」是成本，不是能力

**实战依据**：WorkBuddy（Agent 平台）接入我们的 MCP 服务，即使只有 21 个工具，
仍出现 ① **调错工具**（拿银行回单去调 `invoice_ingest`）② **超时重试导致重复提交**。

**结论**：Agent 数量不解决问题，**边界清晰 + 工具描述准确 + 幂等**才解决。

**建议**：收敛为 **1 个编排 Agent + 3~4 个能力域**：

| 能力域 | 职责 | 对应参考设计中的"Agent" |
|--------|------|----------------------|
| 采集归档域 | 收票（邮箱/卡包/数字账户/拍照/API）、原件归档、多凭证类型 | 采集 + 归档 |
| 识别合规域 | 分级解析、验真、查重、合规校验、风险标签 | 识别 + 验真风控 + 合规审核 |
| 报销应付域 | 事项级报销、无票支出、付款计划、往来核销 | 报销 + 应付 + 业务匹配 |
| 记账税务域 | 科目推荐、凭证、税负、申报底稿 | 记账 + 税务 + 分析 |
| 政策咨询 | RAG 问答（作为**工具**而非 Agent） | 政策咨询 |

其余"专业 Agent"降级为**工具**。**工具描述就是服务目录**（MCP `tools/list`），
必须写明**能力边界与拒绝语义**——这是我们用真实事故换来的结论。

### 风险 2：自动化分级按"风险"分，漏了"可逆性"

参考设计把**归档**列入 L0 全自动。但归档**不可逆**（进电子会计档案后要走销毁流程）。

**建议分级（按可逆性 × 风险双维）**：

| 级别 | 动作 | 说明 |
|------|------|------|
| L0 全自动 | 识别、验真、查重、格式校验、去重 | 纯读取，错可回滚 |
| L1 自动 + 抽检/撤销窗口 | 报销单生成、科目推荐、**归档**（含撤销窗口） | 产出可被人工推翻 |
| L2 人工确认 | 付款、红冲、申报提交、对外发函 | 资金/税务责任 |
| L3 专家介入 | 稽查应对、税务争议、政策适用 | 专业判断 |

### 风险 3：「查验自动化率 100%」是危险指标

**实战依据**：国税查验接口有资质门槛（我们只能先挂 mock provider 并在 UI 标注
"模拟结果"）；接口失败、非正常户、离线部署（数据不出内网）都会发生。

**修订指标**：**验真覆盖率 100% + 查验失败原因可解释 + 失败必进人工**。
"覆盖率"是合规要求（可达成），"自动化率"受外部依赖限制（不可承诺）。

## 二、缺失的关键功能点（9 条，按优先级）

| # | 缺口 | 为什么关键（实战依据） | 已落地的做法（发票易） |
|---|------|---------------------|---------------------|
| **P0-1** | **只提"发票"，漏了银行回单/对账单** | 财会〔2025〕9 号**明列**银行电子回单与对账单为凭证类型；也是"无票支出"与现金流的基础 | 多银行回单解析：模板库（加模板即接入新行）+ 分块 + 页码定位与高亮；可作报销明细 |
| **P0-2** | **非发票文档的边界拒绝** | 否则**静默产生空壳记录**污染发票库（真实发生：银行回单进了发票表） | 边界硬拒绝：零提取且识别能力在位 → 物理删除 + 审计留痕；错误文案**引导正确工具** |
| **P0-3** | **一票一报的强约束** | 防重复报销不能靠"标记"：每刻/汇联易的公开方案也是**发票池查重 + 校验前移** | **DB 部分唯一索引**（active 明细的发票唯一）+ 报销状态正交维度（none/pending/claimed） |
| **P0-4** | **报销的"事项层"** | 实务要求明细逐项写清「发生日期/费用类型/事项说明/票据号」；差旅要行程、采购要三单、招待要对象人数 | 三层：报销单 → **事项**（差旅子类：交通/住宿/市内交通/伙食补助）→ 凭证 |
| **P0-5** | **无票支出的凭证合规** | 28 号公告：小额零星个人可用收款凭证，但**必须**含「姓名 + 身份证号」；超起征点须取得发票 | 凭证类型枚举 + 要素校验 + `deductible` 标记（不可扣除可一键筛出，供汇算清缴） |
| **P0-6** | **费用的税务口径分类** | 招待费（**60% 且 ≤营收 5‰**）与职工福利费（**工资薪金 14%**）是两套限额，归错 = 纳税调整算错 | 六类含「福利费」；团建/聚餐关键词**优先于**餐饮的招待关键词 |
| **P0-7** | **幂等与防重（Agent 场景特有）** | Agent 超时会重试 → 重复建单 / 重复入库（真实发生：同一文件被提交 5 次产生 90 条重复） | 文件 SHA256 唯一（重复 409）+ 批次异步模式 + 单号幂等 |
| **P1-1** | **不可见性体验：周期过滤会把票据"藏起来"** | 用户以为数据丢了（真实反馈："这张发票怎么查不到"） | 「全部」选项 + 「其他周期还有 N 条」主动提示 + 「未归类」单独筛选 |
| **P1-2** | **审计要记"结果"** | 等保要素含「**事件是否成功**」；只记动作不记结果，审计价值减半 | outcome 归一化（成功/已拦截/失败/异常/无成败语义）+ 身份事件分级（登录成败） |

## 三、架构优化建议

### 建议 1：补「证据链关系模型」（参考设计缺）

参考设计提了三单匹配，但缺**统一的关联图**。没有这层，应付、记账、归档会各建各的关联。

```
发票 ─┬─ 事项（费用明细行）── 报销单 ── 审批 ── 付款
      ├─ 合同 / 订单 / 入库单（三单匹配）
      ├─ 凭证（记账）
      └─ 档案包（归档）
```

最小可用形态 = **事项层**（发票易已实现）：它是"业务语义"与"票据"之间的锚点，
向上支撑报销与审批，向下连接凭证与档案。

### 建议 2：补「时限管理」（参考设计完全没提）

财务工作的本质是**按时**：进项勾选认证期、申报期倒排、报销时效、供应商对账周期、
档案保管期限。这是 Agent 最容易做出**付费点**的功能（"到点提醒 + 倒排催办"），
且实现成本低（定时任务 + 规则），建议**提到阶段 1**（数据模型要预留期限字段）。

### 建议 3：Agent 调用的可靠性工程（实战清单）

| 问题 | 做法 |
|------|------|
| 客户端超时（长任务） | **批次异步模式**：立即返回批次号，后台解析，工具轮询状态 |
| 重复提交 | 内容哈希去重 + 唯一约束兜底 + 明确拒绝文案（含已有批次信息） |
| 调错工具 | 工具描述写明边界 + 错误文案**引导正确工具**（不给空壳结果） |
| 工具能力发现 | 利用 MCP `tools/list` 的服务目录；描述要写"适用/不适用" |
| 长尾 LLM 调用 | 规则优先（确定性、可离线）；LLM 仅兜底并要求**结构化输出** |
| LLM 静默失败 | 调用失败必须留痕（我们曾因提示词缺 "json" 导致归类长期静默退化为 other） |

## 六、指标修订

| 参考设计指标 | 修订建议 | 说明 |
|-------------|---------|------|
| 发票自动采集率 > 95% | ✅ 保留 | 邮箱+卡包+账户+导入，可达成 |
| 识别准确率 > 98% | ✅ 保留，拆为**结构化原件/版式件**两档 | XML 应 > 99.9%，OCR 档单独考核 |
| 查验自动化率 100% | ❌ 改为**验真覆盖率 100% + 失败可解释 + 失败必进人工** | 受资质与外部接口限制 |
| 报销处理时长 3 天 → 10 分钟 | ✅ 保留，补**"人工介入率"** | 自动化率与介入率要一起看 |
| 记账自动化率 > 80% | ✅ 保留，补**"科目推荐采纳率"** | 采纳率才是学习闭环的度量 |
| — | ➕ **异常拦截率**（重复报销/非发票/风险票） | 风控价值指标 |
| — | ➕ **时限达成率**（申报/认证/对账按期完成） | 财务工作的本质指标 |

## 附：发票易实战教训（工程落地清单）

1. **LLM 结构化输出**：OpenAI 兼容接口用 `response_format=json_object` 时，
   提示词**必须含 "json" 字样**，否则 DeepSeek 直接 400（我们曾静默退化）
2. **别用 `Decimal(float)`**：SQLite 的 `SUM` 返回 float，会产生
   `2991.1500000000000909…` 长尾污染金额字段——统一量化到分
3. **列表新增参数用关键字传参**：位置参数在签名扩展时会错位（我们的 MCP 分页曾因此失效）
4. **SQL NULL 过滤**：`WHERE date >= x` 会静默排除 NULL 行——缺日期的票据必须有归月/归期兜底
5. **前端周期过滤**：默认"当前月"会让用户找不到票，必须提供「全部」与"其他周期有 N 条"提示
6. **不可逆动作的删除语义**：删除已通过单据**必须释放发票占用**（否则永久卡在"已报销"）
7. **Agent 工具设计**：长任务用批次异步；重试用幂等键；错误文案引导正确工具
8. **多银行解析**：按"模板 + 语料"扩展（加银行=加配置+加测试），不要硬编码；
   整页版面重排不可靠时，改用**局部版面查询**（只对失败字段在标签附近取坐标值）
