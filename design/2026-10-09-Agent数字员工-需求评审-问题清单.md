# 需求评审——问题清单 v1

> 日期：2026-10-09 · 待评：`frd/Agent-Digital-Employee-Requirements-v1.1.md`
> 立场：建设性批判。目标不是挑刺，而是把"实施时会卡住的点"摆到台面。

---

## A. 定义级（不解决，整个文档都有歧义）

### A1. 「AI」的定义边界不清
**问题**：spec 用「AI」「LLM」「Skill」「MCP」「数字员工」几个词，但没定义它们的关系与边界。

- 「数字员工」= LLM？= LLM + Skill？= LLM + Skill + MCP？
- §7.1 ❌1「AI 不得直接操作数据库」—— `auto_review_predictions` 由 system cron 触发，谁算 AI？cron 算「系统」还是「数字员工」？
- §5.3 Skill「不能直接调用传统系统，必须通过 MCP 工具」—— 但当前 `tools_bridge.build_tools_for_user` 是按权限把**全量 MCP 工具**暴露给 LLM。LLM 完全可以绕过 Skill 直接调 `expense_create`，违反 §7.2 ✅7 的字面意思

**建议**：spec 补充「主体分层」段落，明确 LLM / Skill / MCP / 传统系统 / system cron 各自的写权限边界。

### A2. 「审批状态」的定义没列
**问题**：§7.1 ❌3「AI 不得直接改变审批状态」—— 但「审批状态」包括什么？

- `expense_submit` 把 `submitted_at` 写库，是状态变更吗？
- `invoice_unblock` 把 `red_flag` 改掉，是状态变更吗？
- `invoice_classify` 改 `expense_type`，是状态变更吗？

spec 把「状态机」说得像单层，但当前代码里 `Invoice.status` / `ExpenseClaim.status` / `WebTicket.used_at` 三套状态机互相独立，字面照搬 §7 会误伤大量现有流程。

**建议**：spec 明确「审批状态 = 仅指 `ExpenseClaim.status` 的 draft→submitted→approved→paid 四态」。

## B. 逻辑/一致性漏洞

### B1. §4.3 与 §4.4 分类不一致
- §4.3「必须人工」8 项（按岗位/环节）
- §4.4「触发条件」4 类（按条件类型）
- 两者**无覆盖关系**：§4.4 漏了「金额阈值」（>5000 必须人工）；§4.3 漏了「异常不可判定」的对应条件

**建议**：把 §4.3 重写为「按触发条件」一维分类，岗位放到角色授权矩阵里。

### B2. §3 第 3 层「智能建议层（可选）」与 §5.3 5 个 Skill 矛盾
- §3 第 3 层说 AI 建议层是「可选」（验证 PASS 后才进入）
- 但 §5.3 5 个 Skill 全部都包含"AI 给出编排决策"——这是 Layer 3 还是 Layer 4？
- 当前架构图把 Skill 放在 Layer 4（裁决层），但 Skill 又依赖 Layer 3 的 AI 建议——Layer 3 既然可选，Skill 怎么用 AI 建议？

**建议**：把第 3 层改成「必选」或把 Skill 明确分层（编排层 vs 决策层）。

### B3. §6.1 「AI 是隐形后台」与 §6.1 「对话式交互」冲突
- 隐形 = 用户感知不到 AI
- 对话式 = 用户和 AI 直接交互
- 怎么调和？spec 没明说

**建议**：明确「隐形 = 自动化场景（无人值守）；对话式 = 模糊场景（需要追问）」。

## C. §7 约束自相矛盾

### C1. spec 自身违反 §7 ❌1 / ❌3
- §7.1 ❌1「AI 不得直接操作数据库」、§7.1 ❌3「AI 不得直接改变审批状态」
- 但 §4.1「完全固化」表里有「AI 复核自动通过 → 状态机流转」——这就是 AI 直接改审批状态
- 当前代码 `auto_review_predictions`（`parse/ai_review.py:137`）就是这条

**结论**：spec 自己需要明确豁免「system cron 通道的 auto_review」（已默认 `threshold=0`），并把这条豁免写入 spec §7 注释。

### C2. §7.2 ✅6「MCP 写操作需人工确认」与 Web 端流程冲突
- Web 前端 `expenseSubmit` 直接 `POST /api/v1/expenses/...`，绕开 MCP
- 当前架构：Web REST + MCP 双入口
- spec §7 的"两段握手"是给 MCP 的——Web 通道怎么处理？
- 如果 Web 也要两段握手，每次填一个 entry 都弹确认框，UX 极差

**建议**：spec 明示「Web 通道视为人工通道（用户已登录即视为已确认）」，§7 约束仅作用于 MCP/IM 入口。或把所有写入口强制走 MCP（工作量 +30%）。

### C3. §7.2 ✅3「所有决策必须记录审计日志」——「决策」粒度未定义
- LLM 一次工具调用？一次完整回复？一次会话？
- 当前 audit 是动作级（一个工具调用一条记录），LLM 推理过程不记
- 等保三级要求「操作可溯」——推理不记就不达标

**建议**：spec 加 `audit` schema：`actor_type ∈ {user, agent, system_cron}` + `llm_call_id、prompt_hash、model_version` 字段。

## D. 与原 FRD（InvoiceEase-frd-v0.1）的架构冲突

### D1. 原 FRD 是 REST + Web 直连，spec 要求 MCP 中间层
- 原 FRD 第 4 章：Web 后台直接调用 REST API
- spec §5.2：所有能力封装为 MCP Server
- 冲突：当前架构 REST 直连是新功能；要不要把 Web 也改走 MCP？

**风险**：保留双入口 = spec §7 约束不彻底；统一规范 = 重构 Web 前端，工作量大。

**建议**：spec 加一段「通道分层」：Web = 人工通道；MCP/IM = Agent 通道；两通道写策略不同。

### D2. 原 FRD 的 RBAC 与 spec 的 scope 体系不一致
- 原 FRD 角色：`员工/财务专员/财务主管/系统管理员`（4 级）
- 当前代码 `mcp/identity.py` scope 13 个（`invoice:read / invoice:write / invoice:admin / expense:read / expense:write / expense:approve` 等）
- spec §5.2 没要求改 RBAC，但写「写操作需人工确认」实际是把「角色」升级成「主体类型」（user / agent / system）

**建议**：spec 明确 RBAC 是「角色内」权限，MCP scope 是「通道间」权限，两套叠加。

## E. 实施细节漏洞

### E1. 5 个 Skill 的 advertisement 100 token 估算偏紧
- 100 token ≈ 50-75 中文字
- spec §5.3 说"启动时每个 Skill 只消耗约 100 个 token 用于广告"
- 实际要给 LLM 完整路由信息：Skill 名 + 触发场景 + 输出承诺 + 调用工具 + 失败处理——至少 200-300 token
- 风险：广告太短 → LLM 选错 Skill 概率高

**建议**：放宽到 200 token，或把广告做成结构化 JSON 而非散文。

### E2. Skill 多轮对话状态未定义
- spec §6.3 对话式报销发起：用户说"上周去上海出差3天"→ AI 追问 → 用户补充 → AI 生成结构化报销单
- 这是 4 轮以上对话
- spec §5.3 Skill 没说状态持久化：对话中断再回来怎么办？Skill state 在哪？

**建议**：spec 加「Skill State」段落：state 存在哪（Redis? AgentMessage?）、保留多久、如何续传。

### E3. LLM 模型选型未定
- §3 第 1 层「多模态LLM」、第 3 层「AI」、§5.3「Skill」—— 是同一个 LLM 还是多个？
- 多模态（Qwen-VL）和决策推理（DeepSeek）是不同模型；OCR/解析和 NL2SQL 是不同模型
- spec 用「LLM」一词含糊带过

**建议**：spec 加「模型分层」：感知层（多模态）/ 编排层（对话）/ 校验层（结构化抽取）各用哪类模型，并允许配置。

### E4. 实施路线时间估计偏乐观
- 阶段一 1-2 周：5 MCP Server 物理拆分 + 13 个新工具 + idempotency 改造 + pydantic 出参 schema 化
- 实际差距分析显示：13 个 spec 工具里 8 个 ❌ 完全缺失，3 个 🟡 需要重构；叠加 idempotency_keys 表 + 两段握手 + pydantic 全量覆盖
- 现实估算至少 4-6 周

**建议**：spec 阶段一改为 4-6 周。

### E5. AI 增强的成本/性能预算没定
- spec §6.2 列了 5 个 AI 增强点（异常标注、审批建议、费用摘要、报销对话、异常提示）
- 每个增强点 = 一次 LLM 调用
- 100 张发票/月 × 5 增强点 = 500 次 LLM 调用/月
- 当前 `parse/llm.py` 看是无批处理、无缓存
- 风险：成本和延迟都没量化

**建议**：spec 加「LLM 成本预算」：每月调用上限、批处理窗口、降级阈值（如 LLM 超时回退到模板化提示）。

## F. 合规与安全硬伤

### F1. 数据分级与隐私未提
- PRC PIPL 把发票号、金额、报销人识别为敏感个人信息
- 等保三级要求：访问审计、加密存储、备份策略
- 当前 SQLite + 文件存储——能过等保几级？发票原件是不是要加密？

**建议**：spec §9 加「数据分级」：哪些字段加密、保留期、删除权。

### F2. 税务发票云服务商未指定
- spec §9 说"集成税务发票云"
- 航天信息、百望、票易通各有 API 和费率
- 没指定服务商或抽象层
- 当前代码 `verify/mock.py` 是 mock，真接入要选服务商 + 谈商务

**建议**：spec 加「验真服务商抽象层」（`verify/provider.py` 接口），业务侧只看到接口。

### F3. 「数据存储在中国大陆境内」与开发态 SQLite 矛盾
- 当前 `.env` 是本地 SQLite，开发态完全在中国大陆境外机器
- 一旦部署上生产（境外云）就违规
- spec 没明示"生产部署约束"与"开发态可豁免"

**建议**：spec §9 加「部署环境」段落：开发/测试/生产三档约束。

## G. 命名/接口级（细节但实施时会卡）

### G1. MCP 工具命名与当前代码不一致
- spec `search_invoices(email, date_range)` vs 当前 `invoice_list(status, date_from, date_to, keyword, expense_type)`
- spec 想通过 `email` 关联邮件域；当前是按报表询价
- 改名的连锁影响：所有现有 Skill 都要改

**建议**：保留 `invoice_list` 名，加 `email` 入参向后兼容。

### G2. 「发票管理MCP」read-only 与 `extract_invoice` 矛盾
- spec 把 `extract_invoice(file_id)` 列入 read-only
- 当前 `extract_invoice_file` 是写（触发 OCR 流水线、写入数据库）
- spec 把"读"和"写"的边界划在工具能力层，错了——边界应划在副作用层

**建议**：spec 改成按"是否产生副作用"分类（pure read / stateful read / write）。
