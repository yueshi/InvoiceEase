## 一、执行摘要

需求文档定义了 **5 层架构 / 5 个 MCP Server / 5 个 Skill / 10 个 UI 模块 / 7 禁 7 必**。当前 `feat/agent-digital-employee` 分支对应的代码距离合规基线最远处在三块：

1. **协议层**：MCP 写操作没有「两段握手」(proposal → human_ack → execute)，`validate_expense` 整工具缺失 → 7 必里最关键 3 项被破（❌4 / ❌7 / ❌6）
2. **状态机层**：`auto_review_predictions` 仍允许 AI 推进 `invoice.status`（即使默认 threshold=0）；`MCP` 通道的报销动作在审计里被错记为 `channel="web"`（等保「主体」失真）
3. **业务编排层**：5 个 Skill 0 落地（只有 1 个单文件手册 + 1 个万能 MainAgent）；预算/审批路由 service 整体缺位

| 维度 | 规格要求 | 现状 | 覆盖率 |
|---|---|---|---|
| MCP 工具（spec §5.2 13 个） | 13 | ✅ 2 / 🟡 3 / ❌ 8 | **23%** |
| Agent Skill（spec §5.3 5 个） | 5 | 0/5（1 个单文件手册） | **0%** |
| 硬约束 §7（7 禁 7 必 共 14 项） | 14 | ✅ 4 / 🟡 8 / ❌ 2 | **57%**（其中 2 项 fail 是高风险） |
| UI 模块（spec §6.2 10 个） | 10 | 5/10（结构化全有，5 个对话式全缺） | **50%** |
| 跨平台机器人（飞书/钉钉/企微） | 3 | 1/3（企微仅出站） | **入站 0%** |

## 四、硬约束 §7 审计（关键 3 风险）

> 数据源：差距 C 报告（已存档）

### 🔥 风险 ① ❌7 + ❌4：MCP 写操作无两段握手 + 无 `validate_expense`
- LLM 一次调用即可写库（`expense_create / expense_add_* / invoice_update / invoice_unblock / invoice_delete`）
- 「报销单级 validate」整接口缺失 → `expense_submit` 只查「事项非空」，跨字段/超阈值/预算/查重无统一闸门
- **修法**：新增 `validate_expense(claim_id)` MCP 工具；写工具两段式 `*_proposal → confirm_execute(proposal_token, human_ack=true)`；MCP server 层枚举白名单

### 🔥 风险 ② ❌3：`auto_review_predictions` 由 AI 通道直接驱动状态机
- `parse/ai_review.py:137 transition(inv, "pending_submit")` 是「数字员工→invoice 状态机」直接路径
- 即使默认 `threshold=0`，运维误调即可破规
- **修法**：`auto_review_predictions` 只允许 system cron 调用、禁止被任何 MCP/Agent 路径触达；入口 `assert caller == "scheduler"` 护栏；UI 显著标记「数字员工自动通过」

### 🔥 风险 ③ ✅2 + 🟡3：写工具无 idempotency_key + MCP 通道审计 channel 全记成 web
- 重试/网络抖动会重复落库
- `workflow/expenses.py` 所有 `write_audit(...channel="web")` 写死 → 等保「主体」失真
- **修法**：(a) `write_audit` 加 `channel` 形参；(b) 引入 `idempotency_keys` 表，`tools.idempotent_run(key, fn)` 包装；(c) 至少给 `expense_create / expense_add_* / invoice_update / invoice_classify / company_info_save` 加幂等键

## 七、阶段化理由与建议起点

**为什么这样切**：
- P0 是**合规底线**（spec §7），不做 P0 就开始 P2/P3 是沙滩盖楼
- P1 解锁**业务编排**（5 Skill），不做 P1 就直接做 P2 漏斗，LLM 不知道用哪个 MCP 工具
- P2 解锁**体验入口**，P3 解锁**外部入口**——两条独立并行，不互阻

**建议起点（你确认后我们开 plan）**：

| 候选 | 内容 | 工作量 | 风险敞口 |
|---|---|---|---|
| **方案 A**（推荐） | P0 协议合规（4 周） | 中 | 关掉最关键 3 风险 |
| 方案 B | P0 + P1 同步推进（8 周） | 大 | 关风险 + 拿业务能力 |
| 方案 C | 只做 P0 的 ❌7 + ❌4（两段握手 + validate_expense） | 小（2 周） | 先关最危险的两条口子 |

## 八、需你拍板的几个范围问题

1. **起点**：A / B / C 哪个？还是想先只做 P1 的某一块（比如只做 差旅 Skill）？
2. **P0 是否一次性做完**：5 项（P0 表里）是一起出，还是分批？我倾向一次性出，因为它们是同一组「协议层」改动，分批会引入中间态不一致
3. **MCP Server 物理拆分**（P1 最后一项）放 P1 还是 P3？我倾向放 P1，spec 写得很明确，拖到 P3 会让 IM 接入时还得再拆一次
4. **预算 service 的预算模型**：spec 没写明细（按部门？按类别？按期间？混合？）。需要你给一句话定调，否则 P1 起不了手

确认范围后，我会按 writing-plans 规范出 4 份执行 plan（每阶段一份，文件名 `docs/superpowers/plans/YYYY-MM-DD-<name>.md`）。
