# 发票易 · 用户与权限管理设计

日期：2026-09-15 ｜ 状态：**已实施完成** ｜ 关联：[MCP 身份与权限设计](./2026-09-13-MCP身份与权限设计.md)、FRD §3.5.2（RBAC）

---

## 0. 摘要

在既有「四级角色 + 管理员改角色」的基础上补齐账号生命周期管理：
**自助改密、管理员重置（强制下次改密）、暂停/恢复、角色调整**。

核心设计判断：**「暂停」必须在三处同时生效，否则是假的**——只在登录处查，
已签发的 JWT 还能用最长 8 小时，刚建的 MCP 令牌照跑，等于没停。

---

## 1. 现状（改造前）

| 能力 | 状态 |
|------|------|
| 建号 / 改角色 | ✅ 有（`PUT /users/{id}`） |
| 自助改密 | ❌ 无 |
| 管理员重置他人密码 | ❌ 无（只能在 `PUT` 里带 `password`，且无"强制改密"语义） |
| 暂停 / 恢复 | ❌ 无（`users` 表**没有状态字段**） |
| 建号审计 | ❌ 无（建号不留痕） |

关键：`get_current_user` 与 `MCPTokenVerifier` **都不检查用户状态**（当时也没有状态可查）。

---

## 2. 三个闸门（本次要点）

暂停若只在登录处生效，就是"下次登录才生效"——**不是暂停**。三处必须同时做：

| # | 闸门 | 位置 | 效果 |
|---|------|------|------|
| 1 | 登录 | `POST /auth/login` | 暂停用户登不进来；审计带 `reason=suspended`，与"密码错"区分（否则看不出有人在反复撞已停用的账号） |
| 2 | 每个 Web 请求 | `security.get_current_user` | **已签发 JWT 立即失效**，不必等最长 8 小时过期 |
| 3 | MCP 调用 | `mcp/verifier.MCPTokenVerifier` | **Agent 令牌立即失效**；legacy 内建令牌改取"**可用的**最小 id 管理员" |

**暂停不是撤销**：恢复后令牌自动可用（令牌本身没被撤销）。
这样"临时停职"与"永久离职"（撤令牌）是两个不同动作，语义清晰。

### 2.1 强制改密闸门

管理员重置密码后置 `must_change_password`，该用户在 `get_current_user` 里被拦。

**实现要点：默认全拦、白名单放行**（`/auth/password`、`/auth/me`、`/auth/logout`）。

反过来做（逐个接口加"要求已改密"依赖）会漏——将来新增接口忘了加，就是一个洞。
默认拦截只依赖那份**短的、显式的**白名单，新增接口天然被覆盖。

**MCP 通道不受 `must_change_password` 影响**：那是另一套凭据体系，
且与"暂停"性质不同（重置的是 Web 登录密码，不是 Agent 令牌）。这个边界是刻意划的。

---

## 3. 防自锁

把管理能力做强的同时，必须防住"把自己或整个系统锁死"——这类事故只能改库才能救回来。

| 规则 | 性质 |
|------|------|
| **不能暂停自己** | ✅ **真正生效的防线**（API 可达，已测） |
| **不能改自己的角色** | ✅ **真正生效的防线**（API 可达，已测）。最后一个管理员自降 = 系统失管 |
| 不能暂停/降级**最后一个可用管理员** | ⚠️ **防御性规则，经 API 当前不可达** |

**为什么"最后一个管理员"规则不可达**：操作者自身必须是**可用**管理员
（闸门 2 已挡住暂停用户），因此至少还剩一个可用管理员，目标不可能是"最后一个"。
（`create_app()` 的 bootstrap 还会建一个内置 admin，进一步让这种情况不出现。）

那为什么保留？**防将来新增调用路径**（脚本、批量运维、或将来放开"财务主管可停管理员"）。
保留的同时**在代码与测试里写明它经 API 不可达**——否则后人看到注释会误以为系统已经防住了。
`test_last_admin_guard_is_defensive_only` 在 service 层钉住规则本身。

## 4. 数据模型

`users` 加两列（迁移 `c3d4e5f6a7b8`；NOT NULL 均带 `server_default`，SQLite 给有数据的表加非空列的硬要求）：

| 列 | 值 | 说明 |
|----|-----|------|
| `status` | `active` / `suspended` | 用字符串而非 bool：与库内既有风格一致（InvoiceStatus 等），且留了扩展位（如 `locked`） |
| `must_change_password` | bool | 管理员重置后置位 |

---

## 5. 接口

| 方法 | 路径 | 权限 | 说明 |
|------|------|------|------|
| POST | `/auth/password` | 登录用户 | 自助改密，**须验原密码**（防会话被劫持后直接改密） |
| POST | `/users/{id}/password` | admin | 重置：`generate`（自动生成）或 `new_password`（手动指定）；**明文仅在自动生成时回显一次** |
| POST | `/users/{id}/suspend` \| `/resume` | admin | 暂停 / 恢复 |
| PUT | `/users/{id}` | admin | **收窄为仅改角色**；带 `password` 会被拒并提示走 `/password` |
| POST | `/users` | admin | 建号（**补审计**） |

**为什么把密码从 `PUT` 里拿出去**：重置密码还要置"下次登录须改密"，与"改个字段"语义不同；
混在一个接口里，调用方无法表达"我是想重置（强制改密）还是想静默改掉"。

**密码策略**：最少 8 位。**只在校验设置时生效**——存量短密码用户照常登录，
不强制全员重置（避免上线即引发一批无法登录的投诉）。

---

## 6. 审计

六类账号安全事件，归入**安全审计**视图（与 LOGIN 同级，AdminAudit 页的「安全事件」标签页）：

`PASSWORD_CHANGE` · `PASSWORD_RESET` · `USER_SUSPEND` · `USER_RESUME` · `USER_ROLE_CHANGE` · `USER_CREATE`

- 全部记录**操作者**：重置他人密码时 `user_id` 是管理员，`detail.target_username` 是被重置者
- 越权/危险操作的尝试记 `result=rejected` → `outcome=blocked`（**系统正确拦截**，不是失败）
- `USER_ROLE_CHANGE` 记 `from → to`，并带 `active_tokens`（提示管理员：令牌 scope 是签发时固定的）

---

## 7. 角色变更与已有 MCP 令牌（易误解点）

| 维度 | 是否即时生效 |
|------|-------------|
| 数据范围（role） | ✅ 即时——MCP 令牌 claims 每次请求重新组装 |
| 令牌 scope | ❌ 签发时固定。降级后旧令牌可能仍带多余 scope |

**但不会越权**：工具层是「role 与 scope **取交集**」，角色闸门照样拦得住。
要彻底收紧就撤销该用户的令牌（`USER_ROLE_CHANGE` 审计里的 `active_tokens` 就是为此提示）。

### 8.1 实施中修掉的一个契约缺口

后端 `UserOut` schema **漏加 `status` / `must_change_password`**，而前端路由守卫读的正是后者
——**缺字段会让强制改密静默失效**（被重置密码的人照样能进所有页面）。

前端单测用的是 mock 数据，**照不出这类"接口不给字段"的问题**；是端到端跑起来才炸的
（`KeyError: 'status'`）。已补 schema，并加 `test_user_out_exposes_status_and_flag`
在**真实响应**上钉住这两个字段。

> 教训：mock 验证的是"组件怎么用数据"，验证不了"接口给不给数据"。契约字段要在真实响应上钉。

## 9. 明确不做 / 遗留

| 项 | 说明 |
|----|------|
| 删除用户 | 用暂停代替（软停用，保留审计与归属线索；报销单等外键还引用着用户） |
| 登录失败锁定（N 次错误自动锁定） | 与"暂停"不同（自动 vs 人工）；当前靠审计里的 `LOGIN_FAILED` 事后发现 |
| 密码强度规则（大小写/特殊字符/历史密码） | 当前只要求 8 位；企业内控要求更高时可加 |
| 逐人细粒度权限 | 本次明确保持**角色制**（4 档）；细粒度权限需新建权限表 + 与角色取交集的判定逻辑 |
| 用户自助注册 | 企业内网系统，由管理员建号 |
