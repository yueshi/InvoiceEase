> 关联：`design/2026-09-16-运维兜底设计.md`（班表任务/审计）、`docs/运维手册.html`

## 1. 背景与问题

银行回单里有相当一部分交易**本就不会有发票**：

- **税费缴款**（缴款书/完税凭证）——税务机关不开发票；
- **社保/公积金**——社保局/公积金中心不开发票；
- **银行内部费用**（手续费/工本费/结息）——银行出具的凭证即凭证；
- **工资代发**——以工资表/个税申报为凭证；
- **本司账户间调拨**——自己跟自己转账。

但系统当前把这些一律归入「无票支出」：进 `GET /receipts/unmatched` 队列、被月度健康报告统计、被 WorkBuddy 催票工具催「请补开发票」——**催不到，且永久滞留在队列里**，稀释了真正该催的采购类支出。

同时（2026-09-17 已修的两处相邻问题，本设计的起点）：

- 「无票支出」此前连**方向**都不判，收款未配对也混入（commit `98f6a80`）；
- 本司账户行此前对方留空（`no_counterparty`），现记为对应银行并标 `self_account_row`。

本设计把「这笔交易是否需要发票」从零散启发式，升级为**显式分类体系**。

## 2. 核心抽象：性质（category）落库，要求（requirement）由映射派生

```
回单 ──判定──▶ category（落库，可人工覆盖）
                  │
                  └─ CATEGORY_META 映射 ──▶ invoice_requirement（派生，不落库）
                                              │
                        ┌─────────────────────┼──────────────────────┐
                    无票支出队列           催票报表/MCP           凭证类型建议
```

**为什么要求派生而非落库**：策略（哪类要发票）会变，性质（这是什么交易）不会。改策略只改一处映射，不迁移数据。

### 2.1 分类与要求对照表

| category | 中文 | invoice_requirement | 判定依据（按优先级，命中即止） |
|---|---|---|---|
| `social` | 社保/公积金 | `none` | 对方名或摘要命中 `社会保险\|社保\|住房公积金\|公积金管理中心` |
| `tax` | 税费缴款 | `none` | **付方向**且对方名命中 `国库\|税务局\|税务分局\|财政局\|财政部\|海关` |
| `treasury_in` | 财政/补贴/利息收入 | `none` | **收方向**且对方名命中上述机构集合 |
| `bank_fee` | 银行内部费用 | `none` | 摘要命中 `手续费\|工本费\|服务费\|年费\|账户管理费\|利息\|结息`（**不**以本司账户行单独作依据——那是自有账户交易，可能是调拨） |
| `salary` | 工资代发 | `none` | 摘要命中 `代发工资\|工资代发\|薪资\|工资\|奖金` |
| `internal_transfer` | 本司账户间调拨 | `none` | 命中本司账户行（`self_account_row`，对方=银行=自有账户行）或对方名命中本司名称集（self_names）或摘要命中 `调拨\|内部划转\|资金归集\|转存` |
| `sales_collection` | 客户回款 | `issue`（我方开具） | **收方向**兜底 |
| `purchase` | 对外采购/服务支出 | `fetch`（需追发票） | **付方向**兜底 |
| `unknown` | 待定 | `fetch`（保守） | 规则无强证据（如方向/对方名缺失） |

要求的三个取值：`fetch` 需取得发票 · `issue` 需我方开具（销项对账）· `none` 无需。

**误判边界（重要）**：机构名模式收窄到「税务局/国库/社保中心」这类**机构全名**，不匹配「税务师事务所」等仅含"税务"二字的服务商——后者是正常采购，必须继续催票。`unknown` 一律按需发票保守处理并进待核对，误判的代价是"多催一次"而非"漏催"。

## 3. 数据模型与迁移

`bank_receipts` 新增两列（迁移仅加列，不内含业务逻辑）：

| 列 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `category` | String(16) | `unknown` | 交易性质（上表取值） |
| `category_source` | String(8) | `rule` | `rule`（规则判定/重分类产物）或 `manual`（人工覆盖） |

外加 `ix_bank_receipts_category` 索引。迁移提供 downgrade 往返。

**历史数据**由第 4 节的重分类任务回填（一次性手动触发）。

## 4. 判定引擎与重分类

- 判定：`workflow/receipts.py:classify_receipt(r, self_names: set[str]) -> (category, source)`——模块级正则常量（`_RE_SOCIAL` / `_RE_TAX_ORG` / `_RE_FEE` / `_RE_SALARY` / `_RE_TRANSFER`，经 `_hit()` 匹配 `party`/`abstract`；**匹配字段因规则而异，见 §2.1**）在函数内按 **if/elif 顺序判定：顺序即优先级，命中即止**，返回 `(category, "rule")`；性质 → 展示名/发票要求/凭证类型由模块级映射表 `CATEGORY_META` 派生（`requirement_of` / `suggest_voucher_type`）。**加类别 = 加一条 if 分支 + 一行 `CATEGORY_META`**。（2026-09-17 回写：原文所写 `CATEGORY_RULES: list[(category, predicate)]` 规则表在实际实现中不存在。）`self_names` 由调用方一次性载入（`_self_party_names` 同款来源），避免逐行查库。
- **解析入队即分类**：`workers/tasks.py` 落 `BankReceipt` 时同步写 category（新回单零延迟）。
- **可重入重分类**：`reclassify_receipts(db, include_manual=False)` 批量重算写回；**默认跳过 `manual` 行**。
- 触发方式：注册为班表任务 `receipt_classify`，加入运维页手动执行白名单（`_RUNNABLE`）。**不设定时**——解析已即时分类，只有「规则升级后回填历史」需要它，手动跑一次即可。

## 5. 人工覆盖与留痕

- API：`POST /api/v1/receipts/{id}/category`，body `{"category": "..."}`（财务角色）；校验取值合法；写 `category_source="manual"`；
  - 传 `"auto"` 表示**清除人工覆盖**（source 回 `rule` 并按规则重算）；
- 审计：每次变更写 `audit_logs`，action=`RECEIPT_CATEGORY`，detail 含 旧值/新值/来源；前端审计页将 `RECEIPT_CATEGORY` 加入业务操作筛选项；
- 幂等：值未变化时不写审计（与 `confirm-review` 同款口径）。

## 6. 下游口径统一（本设计的重点）

**一处判定，五处一致**——全部改走 `is_unmatched_expense`（`workflow/receipts.py`）：

```python
def is_unpaired_outflow(r) -> bool:              # 队列门：未配对 + 非收方向
    return r.paired_invoice_id is None and r.direction != "收"

def is_unmatched_expense(r) -> bool:
    return is_unpaired_outflow(r) and requirement_of(r.category) == "fetch"  # 无需发票的类别不计入
```

（2026-09-17 终审：谓词本体抽出 `is_unpaired_outflow`，月报「无需发票」行与 `is_unmatched_expense`
共用——此前月报逐字重抄一份，谓词一改就漂移。）

覆盖范围：`GET /receipts/unmatched`、`GET /receipts/period-probe?unmatched=true`、`reports.monthly_health`（无票支出笔数/金额）、`mcp/tools.receipt_report`（催票清单）、前端「只看无票支出」筛选。

其余下游：

| 位置 | 行为 |
|---|---|
| `suggest_pair`（自动配对建议） | 仅 **`requirement == "none"`** 的行直接返回 None（税费/社保/银行费用/工资/调拨/财政收入——不等发票，也不会与发票金额撞车错配）。**`issue` 不在此列**：客户回款仍要配对销项蓝票（D5 销项对账），`!= "fetch"` 这类写法会把它静默挡掉（T2 审查 Important-1，2026-09-17 更正） |
| 报销「加回单」（`workflow/expenses.add_receipt_to_entry`） | 按 category 预选凭证类型：`tax`/`social` → `tax_receipt`（缴款书回单）；其余 → `bank_receipt` |
| 回单列表 API（`_receipt_out`） | 增加 `category`、`category_source`、`invoice_requirement` 三个字段（后者派生） |
| 月度健康报告 | 无票口径修正；**新增一行**「无需发票 N 笔（付方向的税费/社保/银行费用等）」便于财务对账。与「无票支出」行是**互斥分划**（同为未配对的付方向行，按 fetch/none 对半分；**收方向不计入**——结息/财政收入的 requirement 也是 none，但「收款未开票」与「付方向无需发票」是两回事。2026-09-17 终审更正：原文写「其中」，会被读成无票支出的子集，与实际不符） |

## 7. 呈现（前端）

- **列表**：未配对行的「状态」列**按 requirement 三分**（**2026-09-17 T5 审查更正**：原文写 `requirement≠fetch` 一律显示「无需发票」，会把 `issue`（客户回款，**我方需开票**）也盖上「无需发票」章——与 §6 `suggest_pair` 把 `issue` 摘出来的更正同源同错，第二次出现即定稿为此三分）：
  - `fetch` → 「无票」（橙）——需追发票
  - `issue` → 「待开票」（蓝）——我方需开具**销项**发票，不是催票对象，也不是「无需发票」
  - `none` → 「无需发票」（默认灰）——不进催票语义
  - 「只看无票支出」筛选行为不变（后端口径已排除）；
- **详情抽屉**：新增「交易性质」行——显示中文性质 + 来源标记（规则/人工），并提供下拉修改（财务角色）；文案**按 requirement 分档**（同上次更正）：`none` → 「该性质无需发票：缴款书或银行凭证即凭证」；`issue` → 「客户回款：我方需开具销项发票（不进项抵扣）」；`fetch` → 不显示提示；
- **审计页**：`RECEIPT_CATEGORY` 进入业务操作筛选下拉。

## 11. 遗留与既定边界（实施后登记，2026-09-17）

实施与终审已澄清的**已知边界**（不是待办，是设计结论）：

1. **前端状态门 = `paired_invoice_id`，不是 `status`**。二者本会脱钩（删发票时 FK 置 NULL，`status` 残留 `paired`）。已做两件事：删票路径 `_cleanup_dependents_of(..., unlink_receipts=True)` 复位回单；展示层改用 `paired_invoice_id` 作门（`utils/format.ts`）。**新写任何「是否已配对」判断都以 `paired_invoice_id` 为准**。
2. **「收方向 + `fetch` 类」是理论裂缝**：后端队列用 `direction != "收"` 排除，前端状态列不含方向。规则路径**产不出**这种行（收方向只会落到 `sales_collection`/`treasury_in`），只有**人工覆盖**把收方向行标成「对外采购/待定」才会出现——此时前后端不一致源于用户自相矛盾的分类。若将来要闭合，前端也需带 `direction`。
3. **`is_unpaired_outflow` 与 `is_unmatched_expense` 必须共用**（`workflow/receipts.py`）。月报「无票支出」与「无需发票」是**互斥分划**、不是子集关系；「付方向 + `issue`」类两行都不计（同样仅人工覆盖可达）。

## 12. 实施回顾（值得记住的坑）

本分支在**同一个坑上摔了三次**——「把 `requirement != "fetch"` 当作『无需发票』」：

1. **T2**：`suggest_pair` 早退写成 `!= "fetch"` → 客户回款（`issue`）的销项配对被静默挡死；
2. **T5**：状态列写成 `!= "fetch"` → 客户回款被盖上「无需发票」章，抽屉还指引「缴款书即凭证」；
3. **§7 定稿**：同样写法在设计文档里第二次出现，才被定为三分。

**教训**：`requirement` 是**三值枚举**（`fetch`/`issue`/`none`），不是布尔。任何 `!= "fetch"` / `else` 兜底写法都要先问「`issue` 落到哪一支」。终审为此全仓 grep 过 `!= "fetch"`——生产代码现已零命中。

其余值得记住的：

- **假绿比没有测试更危险**：本分支实现了 4 处假绿（`toContain("无票")` 被工具栏复选框满足、`document.body.textContent` 被列表自身满足、集合式断言不锁行归属、`status` 门与队列门不同源）。**断言必须锁「哪个元素的哪个值」**，变异验证（改坏 → 必红）是唯一可靠的验收方式。
- **「一处判定」要连可见面一起收敛**：`is_unmatched_expense` 统一了 5 处取数，但真正的破口在**展示层的门**（前端用 `status`、后端用 `paired_invoice_id`）。口径统一必须覆盖「谁在什么时候显示什么」。
- **删记录类操作要问「谁还指着它」**：`FK ON DELETE SET NULL` 只清指针、不清派生状态（`status`），留下「未配对却显示已配对」的僵尸行。凡是「状态 + 指针」双写的表，删除路径必须一起复位。
