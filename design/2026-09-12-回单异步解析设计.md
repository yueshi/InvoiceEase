# 回单上传异步解析设计（R1.1）

日期：2026-09-12 ｜ 状态：已确认（会话内拍板）

## 背景与问题

建行合并导出回单 PDF（6 页 18 张，税票/转账两种版式混排）上传后：

1. **前端超时**：全局 axios timeout=15s，服务端同步解析 124s（17/19 块规则失败逐块触发 LLM），服务端 200 但浏览器已报错，用户重试 5 次产生 90 条重复。
2. **规则覆盖弱**：税票回单字段标签（付款人全称/收款国库名称）不在规则关键词（对方户名/收款方名称）内；日期「年 月 日2026 05 12」占位乱序无法解析。
3. **无防重**：同一文件可无限重复入库。

## 方案（A + C + 防重）

### A. 异步解析（根治超时）

- 新表 `receipt_uploads`：`id / file_hash(唯一) / file_url / file_type / status(parsing|parsed|failed) / receipt_count / error / user_id / created_at / parsed_at`
- `bank_receipts` 增加 `file_hash` 列（溯源到上传批次）
- `POST /receipts/upload`：分类检查 → SHA256 防重（命中 409）→ 存档 → 建 upload 记录 → 入队 → **立即返回** `{"upload_id", "status": "parsing"}`
- worker 任务 `_parse_receipt_upload`：读原件 → parse_receipts_bytes（分块规则 + 块级 LLM 兜底，异步无超时压力）→ 逐条入库 + 自动配对 → 更新 upload 状态/计数
  - local 模式：daemon 线程（**不得内联**，否则又阻塞请求）
  - redis 模式：arq 任务 `receipt_parse_task`
- `GET /receipts/uploads`：最近上传批次状态（前端轮询）
- 前端：上传即提示「已接收，解析中」，轮询批次状态，完成后刷新列表并提示「N 张（M 张自动配对）」

### C. 规则补强（减少 LLM 依赖）

- 户名关键词补：`收款人全称|收款人户名|收款国库|征收机关`（税票回单的收款方；付款人全称是本司，不能当对方户名）
- 日期补：`年\s*月\s*日\D{0,8}(\d4)(\d1,2)(\d1,2)` 占位乱序模式（CCB 打印版式）
- 目标：真实建行 PDF 规则直解率 ≥17/19（当前 2/19）

### 防重

- `receipt_uploads.file_hash` 唯一索引：同一文件重复上传 409，附已有批次状态提示
- 行级 `bank_receipts.file_hash` 便于后续清理/溯源

## 验收

- 上传请求 <1s 返回；18 张回单约 30-60s 后全部入库（LLM 兜底块在后台跑）
- 重复上传同一文件 → 409
- 纯规则文件上传到可见 ≤5s（无 LLM 调用）
- 全量测试绿；前端冒烟绿
