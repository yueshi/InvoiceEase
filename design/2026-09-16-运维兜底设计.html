1. 目标与非目标

目标

让「单机内网私有化」形态下的系统具备四项兜底能力，全部零新增外部依赖，客户 IT 管理员在 Web 后台完成日常运维：

  • 失败可见——日志落盘轮转、任务执行记录、深度自检
  • 异常可达——企微告警带冷却防抖
  • 可恢复——数据库 + 原件的定时备份与恢复脚本
  • 容量可视——磁盘 / 存储用量与阈值告警

非目标（YAGNI）

  • 不做 Prometheus / Grafana / Loki 标准栈
  • 不做调度器拆独立 worker 进程
  • 不做告警恢复推送（v1 页面状态可见即闭环）
  • 不做 JSON 结构化日志
  • 不通过 MCP 暴露任何运维能力

2. 总体架构

新增包 backend/src/invoicing/ops/，6 个单元各司其职：

ops/
├── logging_setup.py     # dictConfig + 按大小轮转落盘
├── checks.py            # 启动自检 + /ops/status 深度自检（同一套检查函数）
├── instrumentation.py   # 任务埋点装饰器 + APScheduler 事件监听 → task_runs
├── metrics.py           # 指标 = 现场聚合查询（无新表、无内存快照）
├── alerts.py            # 告警规则评估（班表任务）+ 冷却防抖 + 复用 notify()
└── backup.py            # SQLite 快照 + 原件打包 + 保留轮转
指标设计取舍：单机私有化数据量小，invoices / audit_logs / task_runs 即事实来源， /ops/status 与告警评估共用 metrics.py 聚合查询现场计算；uptime 等无库信息存进程内存变量。 避免指标表与事实表双写的状态不一致。
调度器单点立场：班表留在 API 进程内（现状），以「可见 + 可恢复」代替进程拆分—— 全任务埋点、EVENT_JOB_MISSED 监听记 missed、misfire_grace_time / coalesce 补跑、 连续失败告警、运维页手动触发。API 进程重启后 APScheduler 由 lifespan 自动恢复。

3. 数据模型（1 个 alembic 迁移，两张新表）

task_runs —— 任务执行记录

字段类型说明
idPK
task_namestr任务名（mailbox_poll / review_predict / monthly_health / audit_retention / ops_check / ops_backup / parse / verify / receipt_parse）
triggerstrscheduler / manual / enqueue
started_at / finished_atdatetimenaive-UTC，全库既有约定
duration_msint nullablemissed 无耗时，为 NULL
outcomestrsuccess / failed / error / missed
errortext nullable异常摘要（类型名 + 消息，不泄敏感值）
detailJSON nullable任务自定义上下文（如邮箱 id、发票 id）

索引：(task_name, started_at)。outcome 语义：success=正常完成（邮箱轮询 0 新邮件也算 success）；failed=业务性未达预期（如备份校验失败）；error=异常抛出；missed=调度器判定错过未执行。

ops_alerts —— 告警历史

字段类型说明
idPK
rule_keystr规则标识（如 task_failed.mailbox_poll、backup.missing）
severitystrcritical / warning
messagestr人读文本（含企微推送原文）
detailJSON nullable触发现场数据
fired_atdatetime
cooldown_untildatetime该规则下次允许再推送的时间

索引：(rule_key, fired_at)。

备份不落表：文件系统即事实源——{ops_backup_dir}/invoiceease-backup-YYYYMMDD-HHMMSS.tar.gz + 同名 .meta.json（备份时间、alembic 版本、关键表计数）。列表页扫目录，杜绝表与文件不一致。

4. 日志落盘（logging_setup.py）

  • dictConfig 在 create_app() 最早期执行；root logger → 控制台 + RotatingFileHandler（{log_dir}/invoicing.log，默认 10MB × 9 份）。
  • INVOICING_LOG_LEVEL 首次被消费（现状：config.py 定义了但全仓无引用）；uvicorn、apscheduler logger 汇入同一文件。
  • 脱敏 Filter：对消息与 extra 中 password / token / secret / key 字样的值打码为 ***；uvicorn access log 不记请求头，Authorization 不落盘。
  • 不做 JSON 格式开关。

5. 启动自检（checks.py）

lifespan 启动时执行一次；同一套检查函数供 /ops/status 随时重跑。结果三处可见：日志、ops_alerts（critical 级）、运维页首屏。

检查项处置
Fernet key 非法（≠44 字节 base64）warn + 显式日志「加密数据重启后将无法解密」（R1 探针；strict 下阻断）
jwt_secret / mcp_token / admin_password 仍为默认值warn（strict 下 fail-fast）
存储目录 / 日志目录 / 备份目录可写失败即阻断启动（硬前提）
DB 连接 + alembic 版本 vs 代码迁移 headwarn「需执行 alembic upgrade head」
磁盘剩余 < 10%warn
OCR / LLM 配置状态info 级展示（能力现状，非故障）

新配置：startup_checks_strict（默认 false）、ops_backup_dir（默认 ./data/backups）。

与 M1 安全基线的边界：本轮只做探针 + 告警；fernet key 无效时拒绝加密落库（根治 R1）属 M1 安全修复，不在本设计内。

6. 任务可观测（instrumentation.py）

  • 班表任务：setup_scheduler 统一包埋点（trigger=scheduler），记录 task_runs；APScheduler 事件监听器捕获 EVENT_JOB_ERROR / EVENT_JOB_MISSED → outcome=error / missed；misfire_grace_time + coalesce 配置补跑。
  • 队列任务：workers/tasks.py 三个任务（parse / verify / receipt_parse）出入口埋点（trigger=enqueue），local 与 redis 两模式均覆盖。
  • 手动触发：trigger=manual。
  • 埋点装饰器自身永不抛异常：任务崩溃时埋点必须存活并记录（try/except 包裹记录动作本身）。

7. 告警规则（alerts.py）

班表任务 ops_check 每 5 分钟评估全部规则：

#规则rule_key阈值（可配）级别
1班表任务连续失败task_failed.{name}同任务 ≥3 次critical
2收取通道疑似瘫痪mailbox.stalledenabled 邮箱的 last_polled_at 超过 2×poll_interval_seconds 未更新critical
3备份缺失 / 失败backup.missing / backup.failed过备份时刻 2h 无今日备份 / 备份任务失败critical
4磁盘将满disk.low剩余 <10%warning
5待复核积压review.backlog>50 持续 2hwarning
6解析异常率parse.error_rate近 1h error 占比 >20% 且 ≥5 张warning
  • 防抖：每规则独立 cooldown_until（默认 4h），冷却期内只落库不推送。
  • 送达：复用 notify()（企微 markdown，含 severity 前缀与系统标识）；发送失败仅日志不阻断。
  • 恢复不推送（v1）：规则恢复正常即不再触发，运维页当前状态可见即闭环。
  • 规则 5 / 6 为业务健康告警，如需收窄为纯系统告警可直接删除，不影响其余规则。

8. 备份恢复（backup.py）

  • 内容：SQLite 一致性快照（sqlite3.Connection.backup()，不阻塞业务写入）+ data/originals/ 打包 + .meta.json，合并为一个 tar.gz。
  • 时机：班表任务 ops_backup 每日 02:17（错开 audit_retention 03:17）；运维页手动触发。
  • 保留：默认 7 份（ops_backup_retention 可配），超出删最旧；手册建议客户将 ops_backup_dir 指向第二块数据盘或网络盘。
  • 恢复：backend/scripts/restore_backup.py——停服 → 解包 → 替换 DB 与原件目录 → alembic upgrade head 校验版本 → 起服。操作手册按用户约定写入 docs/（HTML，浅色主题）。
验收标准：备份 → 恢复 roundtrip 自动化测试，恢复后 invoices 计数与原件文件数一致。

端点方法功能
/ops/statusGET深度自检全项结果 + 指标聚合（版本 / uptime / DB 体积 / 原件体积 / 磁盘 / 最近备份 / 近 24h 业务量）
/ops/tasksGETtask_runs 列表（按 task_name / outcome / 时间过滤 + 分页）
/ops/tasks/{name}/runPOST手动触发白名单班表任务（mailbox_poll / review_predict / monthly_health / audit_retention / ops_check / ops_backup）
/ops/alertsGET告警历史（severity / 时间过滤 + 分页）
/ops/backupsGET备份目录扫描列表（含 meta）
/ops/backups/runPOST手动备份
/ops/backups/{name}/downloadGET备份下载（流式，鉴权）
/ops/logs/tailGET日志尾部（行数参数，默认 200 行，上限 2000）
/ops/logs/downloadGET当前日志文件下载（流式）

MCP 面不新增任何 ops 工具。审计：手动触发 / 备份 / 下载等运维动作记审计日志（action 前缀 OPS_）。

10. Web 运维页（/ops，adminOnly）

  • 路由挂 adminOnly: true（复用现有守卫模式）；新增 web/src/api/ops.ts + views/OpsView.vue。
  • 顶部状态卡片行：版本 / uptime / DB 体积 / 原件体积 / 磁盘剩余 / 最近备份时间。
  • 四个 Tab：任务（runs 列表 + 失败详情抽屉 + 白名单任务手动触发按钮）、告警（历史列表）、备份（列表 + 手动备份 + 下载）、自检（status 全项 + 日志尾部查看 / 下载）。
  • 组件测试沿用现有 Vitest + @vue/test-utils 模式。

12. 错误处理原则

  • 埋点记录动作自身 try/except，永不传染任务。
  • 告警推送失败仅日志（与现有 notify() 语义一致）。
  • 备份任务失败 → task_runs outcome=failed/error + 触发 backup.failed 告警。
  • ops 端点异常返回标准 HTTPException，无全局处理器依赖（与现状一致）。
  • 下载端点流式响应，整文件不读入内存（吸取 S3 分支「整文件读内存」的教训）。

14. 实施顺序建议（供 writing-plans 参考）

  1. 迁移 + 两张表 + instrumentation（班表与队列埋点）——其他一切的地基
  2. logging_setup + checks（启动自检）
  3. backup（含 roundtrip 测试）+ restore 脚本
  4. alerts（规则 + 防抖 + notify 接线）
  5. REST api/ops.py + 审计
  6. 前端 OpsView + api/ops.ts
  7. docs/ 运维手册（HTML）
