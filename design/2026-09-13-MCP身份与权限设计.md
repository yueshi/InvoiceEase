## 0. 结论摘要

> **实施结果（2026-09-15）**：阶段 1 已完成。MCP 通道现在按令牌识别用户，
  数据范围隔离与 scope 校验生效，审计可回答"谁、用哪个令牌、做了什么"。
  端到端实测：员工令牌调 `invoice_list` 与管理员同一调用结果不同（0 条 vs 9 条），
  撤销即时 401。**升级零中断**（legacy 令牌行为与升级前等价）。
  详见 §5 实施计划与 §5.1 实施记录。

1. **原状（问题出发点）**：MCP 通道是**一个静态 token = 管理员通道**。没有用户身份、没有角色校验、审计到不了人。Web 通道的 RBAC 达标，MCP 通道不达标 —— 而 FRD 把 MCP 列为核心集成方式（"员工只需转发邮件，WorkBuddy 对话即完成"）。
2. **不要自己写认证中间件**：MCP Python SDK **已内置规范级认证栈**（`TokenVerifier` → 401/403 + `WWW-Authenticate` + ContextVar 上下文）。本设计只需实现 `TokenVerifier.verify_token()` 一个方法。
3. **分两阶段，接口不变**：
   - **阶段 1（本设计主体）**：per-user 令牌表 + `TokenVerifier` 实现 + 工具层 scope 校验 → **立即可产品化**
   - **阶段 2**：把 `TokenVerifier` 实现换成 OAuth 2.1 / OIDC 校验（对接企业 IdP）→ **规范符合**，业务层零改动
4. **已实测验证**（附录 B）：同步工具函数能读到认证上下文（`subject` + `scopes` 完整），SDK 对无 token 请求返回 401。设计不建立在假设上。

## 1. 背景：现状体检

### 1.1 三层现状（含证据）

| 层 | 现状 | 证据 |
|----|------|------|
| **鉴权** | 全服务**一个**静态 Bearer token；`compare_digest` 防时序比对；无用户绑定/过期/撤销/scope | `mcp/auth.py:15-25`、`config.py:22` |
| **身份** | 合成 `User(id=0, username="mcp", role=admin)`（内存对象，不落库） | `mcp/tools.py:28-30` |
| | 报销类因外键约束改用"库内 id 最小的 admin"当归属人 | `mcp/tools.py:261-275` |
| **权限** | 无任何角色校验；service 层的角色判断在 MCP 下**全部通过** | 见下表 |
| **审计** | `write_audit(..., channel="mcp")` 多数**不带 `user_id`** | `mcp/tools.py:47/143/189/246/471/491/506/604/629` |

### 1.2 管理员身份带来的具体后果

| 校验点 | 位置 | admin 身份的后果 |
|--------|------|------------------|
| 数据范围 | `workflow/services.py:16-20` `_scope_query` | 只有 `role == employee` 才过滤 `user_id == 自己` → **看全公司** |
| 财务专属 | `workflow/expenses.py` `_is_finance` | admin 在 `_FINANCE_ROLES` 内 → **审批、删除他人单据全部放行** |
| 归属校验 | `_require_owner_draft` | MCP 建的单归给"最小 id 的 admin" → MCP 后续都能改 |

唯一真实边界是文件读取白名单 `INVOICING_WORKBUDDY_INBOX_DIR`（`mcp/extract.py:38-41`）。

### 1.3 与 FRD 的差距

| FRD 要求 | 出处 | 现状 |
|----------|------|------|
| 分角色权限管控（四角色） | §3.5.2、§20 产品定位 | Web ✅ / **MCP ❌** |
| 发票列表/详情"权限隔离" | §3.5.1 功能表 | Web ✅ / **MCP ❌** |
| 验收："普通员工仅能看到本人发票，财务可看全公司" | §380 | Web ✅ / **MCP ❌** |
| SSO/OAuth2.0（可选，增强版） | §240、§362 | 未实现（本设计阶段 2） |

### 1.4 规范与产品化差距

MCP 规范的立场（HTTP 传输）：服务器是 **OAuth 2.1 Resource Server**（只校验令牌，不签发、不登录）；每个请求 **MUST** 带 Bearer；**MUST** 校验令牌是为自己签发的（RFC 8707 Resource Indicators）；静态 API key 因**无用户身份、无过期轮换、难以按用户审计**而不满足要求。

这三条正是我们的体检结果——**不是巧合，是"用静态 key 做 HTTP MCP"的固有症状**。

产品化视角更硬：**静态 key 止步 = 每接一个客户人工发一次令牌、离职靠人记得撤销**，是项目制而非产品。

## 2. 目标与非目标

### 目标
1. MCP 通道**每个调用都能定位到具体用户**，并据此做数据范围隔离与角色校验
2. 令牌**可签发、可撤销、可过期、可限权（scope）**，且审计可追溯到"哪个令牌"
3. 架构上**为 OAuth 2.1 留好位置**：阶段 2 只换实现，业务层不改
4. 兼容现有 WorkBuddy 配置（不因升级而中断）

### 非目标（本设计不做）
- **多租户隔离**（FRD E3 代账多企业）：本设计只把 `tenant_id` 落进令牌与审计，**不做全量查询过滤**（那是独立项目）
- 令牌自助注册/动态客户端注册（DCR）：阶段 2 视 IdP 能力
- 前端 OAuth 登录改造（Web 通道仍用现有 JWT）

## 3. 方案选型

### 3.1 为什么不用"自己写中间件 + 自签 token 校验"

现状的 `MCPAuthMiddleware` 是自研 ASGI 中间件。继续自研意味着要自己实现：401/403 语义、`WWW-Authenticate`、scope 比较、上下文传递、session 归属校验 —— 而 **SDK 已经全部实现了**（§4.1）。自研只会偏离规范。

### 3.2 为什么分两阶段而不是直接上 OAuth

| 维度 | 阶段 1（静态 per-user 令牌） | 阶段 2（OAuth 2.1 / OIDC） |
|------|------------------------------|------------------------------|
| 前置依赖 | 无 | 企业 IdP（企微/钉钉/Entra）或本机 AS |
| 客户可用性 | **立即**（离线部署可用） | 需 IdP 就绪 |
| 令牌分发 | 发票易签发（自助/管理员） | IdP 签发，免人工 |
| 规范符合性 | 部分（仍是静态 key，但已有身份/scope/过期） | **完全** |

阶段 1 的**每个字段都出现在阶段 2**：`scopes` → OAuth scope；`expires_at` → `exp`；`user_id` → `sub`；`tenant_id` → claims。所以阶段 1 不是"临时方案"，而是**同一模型的第一种实现**。

## 4. 架构设计

### 4.1 认证链路（SDK 提供 vs 我们实现）

```
客户端  Authorization: Bearer <token>
   │
   ▼  ┌─────────────────────── SDK 自动装配（我们只配置） ───────────────────────┐
      │ AuthenticationMiddleware(BearerAuthBackend)   ← 提取凭据，调 verify_token │
      │ AuthContextMiddleware                          ← 存入 ContextVar        │
      │ RequireAuthMiddleware(required_scopes)          ← 401 / 403 + WWW-Auth   │
      └────────────────────────────────────────────────────────────────────────┘
   │
   ▼  ┌──────────── 我们实现（阶段 1）────────────┐
      │ MCPTokenVerifier.verify_token(token)        │ ← 查 mcp_tokens 表
      │   → AccessToken(subject=user_id, scopes=…)  │
      └─────────────────────────────────────────────┘
   │
   ▼  ┌──────────── 我们实现（工具层）─────────────┐
      │ current_principal()  ← 读 SDK ContextVar    │
      │ @requires("invoice:write")  声明式 scope    │
      │ → 交给 service 层（现有 RBAC 自然生效）      │
      └─────────────────────────────────────────────┘
```

**配置方式**（`mcp/server.py`）：

```python
server = MCPServer(
    "发票易",
    auth=AuthSettings(
        # 阶段 1 不用 AS，issuer_url 仅为满足 AuthSettings 的必填约束（实际不参与校验）；
        # 阶段 2 接 IdP 时才真正启用。
        issuer_url=settings.mcp_issuer_url,
        resource_server_url=settings.mcp_resource_url,  # 用于构造 WWW-Authenticate 的 resource_metadata
        required_scopes=settings.mcp_required_scopes,   # 服务器级最低门槛（取值见 R2）
    ),
    token_verifier=MCPTokenVerifier(),  # 阶段 2 换成 OAuthTokenVerifier
)
```

SDK 约束（已核实 `mcpserver/server.py:237-242`）：`auth_server_provider` 与 `token_verifier` 互斥；两者都不能在没有 `auth` 设置时单独给。

**免费获得**（SDK 已实现，已核实 `auth/middleware/bearer_auth.py:93-115`）：
- 401 `invalid_token`（无/坏令牌）、403 `insufficient_scope`（scope 不足），均带 `WWW-Authenticate`
- **session 归属校验**：SDK 用 `principal_components(token) = (client_id, iss, sub)` 比对"当前请求者"与"创建 session 者"，**防止 A 创建的会话被 B 的令牌复用**（`bearer_auth.py:28-33`）

### 4.2 身份模型

```python
@dataclass(frozen=True)
class Principal:
    user_id: int | None      # None = 内建/系统身份（如 legacy 令牌）
    username: str
    role: str                # 数据范围依据（复用现有 RBAC，不新造）
    tenant_id: str
    scopes: frozenset[str]   # 能力上限
    source: str              # "token" | "legacy" | "oauth"
    token_id: int | None     # 审计用：哪个令牌
```

**关键设计：scope 与 role 是两个正交维度**

| 维度 | 回答的问题 | 来源 | 校验处 |
|------|-----------|------|--------|
| `role` | 这个人**能看到哪些数据** | `users.role` | service 层（已有，不动） |
| `scopes` | 这个令牌**能调哪些工具** | `mcp_tokens.scopes` | 工具层装饰器（新增） |

判定 = **两者取交集**（`role` 允许 **且** `scope` 允许）。这样同一个财务可以给 Agent 只发"只读令牌"——**最小权限**。

### 4.3 数据模型 `mcp_tokens`

| 列 | 类型 | 说明 |
|----|------|------|
| `id` | int PK | |
| `token_hash` | str UNIQUE NOT NULL | `sha256(明文)`；**明文不落库** |
| `token_prefix` | str NOT NULL | 前 8 位，供 UI 展示与审计辨识（不可用于认证） |
| `name` | str NOT NULL | 如"张三的 WorkBuddy" |
| `user_id` | FK users.id NOT NULL | 归属人 → 决定 role 与数据范围 |
| `tenant_id` | str NOT NULL default `"default"` | 为多租户预留（本设计只落值，不做过滤） |
| `scopes` | str NOT NULL | 逗号分隔，如 `invoice:read,expense:write` |
| `expires_at` | datetime NULL | **签发默认 90 天**（`settings.mcp_token_default_expires_days`）；NULL 仅留给服务身份；过期即拒绝 |
| `revoked_at` | datetime NULL | **撤销优先于删除**（保留审计线索） |
| `last_used_at` | datetime NULL | 识别僵尸令牌（支撑"多久没用就撤"） |
| `created_by` | FK users.id NULL | 自助=本人；管理员代发=管理员 |
| `created_at` / `updated_at` | datetime | |

**设计要点**
- **只存哈希**：明文仅在创建时返回一次（UI 一次性展示 + 复制按钮）
- **前缀保留**：让"审计里这个 token 是谁的"可人工辨认
- **不删只撤**：删除会丢失"这个令牌做过什么"的追溯起点
- **限期为默认**：`expires_at` 缺省 90 天（见下）
- **issuer 进 claims**：`claims["iss"]`，为阶段 2 多 IdP 的复合键预留（见 §9 R4）

**有效期默认策略**：Agent 令牌是长期配置（不像会话令牌几分钟就换），太短会逼用户反复重配，无限期又等于放弃唯一的时效约束。取 **90 天默认**，UI 提供 30/90/180/365 天与"永久（不推荐，红字提示）"选项；列表对"30 天内到期"给续期提示。

### 4.5 工具层取身份（38 个工具的收敛）

**关键约束（已核实）**：SDK 只支持**服务器级** `required_scopes`；`ResourceSecurity` 是 URI 模板路径穿越防护，**不是** scope 校验。因此**工具级 scope 必须自己做**。

集中在两处实现，38 个工具各加一行声明：

```python
# mcp/identity.py
def current_principal() -> Principal:
    """读 SDK 认证上下文（ContextVar，已实测穿透到同步工具函数）。
    无令牌 → legacy 内建身份（兼容期）；都无 → 抛错（不应发生，SDK 已拦）。"""

def requires(*scopes: str):
    """工具级 scope 声明：任一缺失 → 抛 ToolScopeError（MCP 以 is_error 返回，文案引导）。"""
```

```python
# mcp/server.py
@server.tool(description="…")
@requires("invoice:read")
def invoice_list(...): ...
```

**当前身份用法与目标的对应**（四类现状 → 统一）

| 现状 | 工具数 | 目标 |
|------|--------|------|
| `_mcp_admin_user()` 合成 admin | 2 | `current_principal()` → 真实 User（`user_id`） |
| `_mcp_real_user(db)` 查最小 id admin | 10 | 同上（**这 10 个正是报销/销项域，最需要真实归属**） |
| 传 `None` 给 service（审计无主体） | 3 | 真实 User + 审计主体 |
| 不涉及用户（主数据/回单/报表） | 21 | 真实 User（审计主体）+ scope 校验 |

改造后 `_mcp_admin_user` / `_mcp_real_user` **删除**（保留为 legacy 兼容路径的唯一实现处）。

### 4.6 兼容与迁移（legacy 令牌）

**必须保证**：升级后 WorkBuddy 现有配置（`INVOICING_MCP_TOKEN`）继续可用，否则现场直接中断。

方案：`MCPTokenVerifier` 先比对配置的 legacy token，命中则返回**内建 admin 身份**：

```python
AccessToken(token=..., client_id="legacy-builtin", scopes=ALL_SCOPES,
            subject=<最小 id admin 的 id>, claims={"source": "legacy"})
```

- 权限等价于现状（不收紧、不放松）→ **零中断升级**
- 审计记 `source="legacy"` + `token_id=None`，UI 标注"内建令牌，建议改用个人令牌"
- 新部署默认**不生成** legacy token（`INVOICING_MCP_TOKEN` 留空即禁用）

**阶段 1 之后的下线路径**：客户按用户签发个人令牌 → 观察 `last_used_at` → legacy token 无流量后移除配置。

**回归重点**：`test_mcp_http.py`（401 断言不变：状态码相同）、`test_mcp_integration.py`（legacy token 继续通过 = 零中断的验证点）、Web 通道不受影响。

## 6. 阶段 2：OAuth 2.1 Resource Server

**接口不变的换实现**：

```python
class OAuthTokenVerifier:            # 与 MCPTokenVerifier 同协议
    async def verify_token(self, token: str) -> AccessToken | None:
        # 1) 校验 JWT 签名（JWKS，带缓存）
        # 2) 校验 iss / exp / aud == 本服务 resource_server_url（RFC 8707）
        # 3) sub → users 表映射（或 JIT 建用户）
        # 4) 按 IdP group/role claim 映射 scopes
```

**新增配置**：`INVOICING_MCP_AUTH=static|oauth`、`oauth_jwks_url`、`oauth_issuer`、`oauth_audience`、`oauth_subject_claim`、`oauth_scope_claim`。

**SDK 已具备的配合能力**：`AccessToken.resource`（RFC 8707）、`claims`（放 `iss`/`act`）、`build_resource_metadata_url` + 受保护资源元数据端点（RFC 9728）、`create_auth_routes`（若我们自任 AS，本项目不走这条）。

**企业 IdP 对接**：企微 / 钉钉 / Entra ID 的 `sub` 映射到 `users`；离职即失效（无需人工撤令牌）——这是阶段 2 的产品价值。

### 6.1 为什么是阶段 2 而不是现在

阶段 1 已覆盖 OAuth 能给的绝大部分价值（身份、scope、过期、撤销）。**只有两件事是 OAuth 独有的**：

| 只有 OAuth 能做 | 当前是不是瓶颈 |
|----------------|---------------|
| 离职自动失效（IdP 禁用即失效） | 否 —— 单企业几十~几百人，靠离职流程加一步撤令牌可兜住 |
| 令牌免人工分发 | 否 —— 已有自助签发，平台侧也支持按用户配令牌 |
| 规范完全符合 | 不是痛点，是**战略期权**（除非平台方明确要求标准 OAuth） |

而成本是实打实的：内网 AS 部署（离线约束下必须自建）、JWKS 缓存、多 IdP 适配、测试矩阵。**保持期权、不提前支付**——阶段 2 的接入成本已被压到"换一个 `TokenVerifier` 实现"。

### 6.2 启动触发器（满足任一即启动）

| 触发器 | 判据 |
|--------|------|
| **客户要 SSO** | 采购清单出现"统一身份认证"（FRD §240/§362 本就把它列在增强版） |
| **平台方要求标准 OAuth** | 接入新 Agent 平台时对方不接受静态令牌配置 |
| **令牌运维出过事** | 离职令牌未撤导致越权——比任何成本论证都有说服力 |
| **多租户 / 代账（E3）** | 身份必须来自外部 IdP 才能规模化，租户隔离同步立项 |

### 6.3 明确不做：自签 JWT 充当中庸方案

看起来诱人的中间路线是"自己签发 JWT、无状态校验、短时效"。**这是最差解**：

- 仍要我们签发 → **分发问题没解决**
- 仍靠人撤 → **离职问题没解决**
- 多了密钥管理成本
- 且自己签发的 JWT **不满足 MCP 规范**（规范明确服务器是 Resource Server，"never issues tokens or logs users in"）

半只脚踏进 OAuth，拿到了成本没拿到收益。要么静态令牌（阶段 1），要么真 OAuth（阶段 2）。

## 8. 验收标准

1. 一个员工的 MCP 令牌调用 `invoice_list`，**返回结果只含本人上传的发票**（FRD §380）
2. 撤令牌后**下一次调用立即 401**（无需重启服务）
3. 缺 `expense:approve` 的令牌调 `expense_approve` → **403 / 工具错误**，且**审计留痕**
4. 每次 MCP 写操作的审计记录**能回答"谁、用哪个令牌、做了什么、结果如何"**
5. legacy 令牌升级后**行为与升级前完全一致**（零中断）
6. 阶段 2 只需替换 `TokenVerifier` 实现 + 加配置，**不改任何业务代码**

## 10. 落地形态（Q3 确认后定稿）

**平台侧已确认**：WorkBuddy 支持给不同用户配置不同 MCP 令牌（2026-09-15）。因此：

### 10.1 部署形态：一人一令牌

```
员工 A 登录发票易 Web → 「我的令牌」自助签发 → 复制
        ↓
在 WorkBuddy 配置该令牌（平台侧按用户隔离）
        ↓
A 的对话里所有 MCP 调用 = A 的身份 → 只看得到 A 自己的发票（FRD §380 达成）
```

**新部署建议直接走个人令牌**，不要生成 legacy 全局令牌。

### 10.2 legacy 令牌的定位变化

从"过渡期主线"降为**纯兼容兜底**：只为不中断既有 WorkBuddy 配置而保留，UI 明确标注"内建令牌（建议改用个人令牌）"，并在其零流量后移除配置（见 §4.6 下线路径）。

### 10.3 对交付顺序的影响

| 步 | 原顺序 | 调整 |
|----|--------|------|
| 步骤 7（令牌管理 API + Web 页面） | 靠后 | **提前到步骤 4~5 之后**——平台侧能配个人令牌，但没有签发界面就没法用，它是主路径而非收尾工作 |
| 验收 1（FRD §380 员工只看自己） | 阶段 1 可验 | **不变，但现在可完整交付**（原先若平台不支持，"各自身份"要等阶段 2） |

### 10.4 实施注意

- 令牌 `name` 建议含用户名（如"张三的 WorkBuddy"）——平台侧配置时便于人工辨识
- 「我的令牌」页面需要**一次性明文展示 + 一键复制**（明文不落库，关闭后不可再取）
- 管理员代发场景要记录 `created_by`，便于"这个令牌是给谁开的"
