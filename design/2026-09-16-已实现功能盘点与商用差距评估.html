一、一句话结论

发票易当前是一个功能面超预期、工程纪律良好的「单租户内网 MVP」：采集/解析/查重/复核/报销/回单/报表/MCP Agent 全链路真实可用，测试密度高（493+39）；但它离商用之间隔着五类硬差距——验真仍是模拟（合规硬约束）、生产部署形态不存在、多租户是空架子、安全基线未达标、若干外部依赖未落地。

按目标口径分级：

商用口径距离
内部试点 / PoC（单企业、有人值守）基本就绪。差 OCR 部署、真机验收、运维兜底
单企业私有化商用差一个生产化里程碑：部署物 + 安全基线 + 验真合规口径
多租户 SaaS架构级差距：tenant_id 仅是摆设，隔离无强制，改造量大

二、已实现功能清单（按能力域，含实现细节）

A. 发票采集与归档（已上线）

  • 双通道邮箱收取：IMAP（imaplib，UID 游标 + \Seen 标记，fetch/imap.py）与 Agently CLI（子进程调用，created_at 游标，限流 10 次/分、200 次/时、单轮 8 封，fetch/agently.py）。调度器每 60s 检查各邮箱 poll_interval_seconds（scheduler.py:65）。
  • 附件合规过滤：PDF/OFD/XML/ZIP（递归取内层原件）→ 收；图片 → 拒收并向发件人回提示邮件（SMTP 或 agently +reply，fetch/filters.py、fetch/reply.py）。
  • 防重复收取：(email_message_id, file_url) 复合唯一索引兜底（models/invoice.py:37-44），撞索引记 duplicate_email 审计。
  • 员工交票上传：仅 PDF/OFD/XML，图片 422 引导走邮箱（api/invoices.py:48-56）。
  • 销项导入：已开票文件导入（红票自动关联蓝票）+ 开票清单 CSV/Excel 批量导入（api/invoices.py:59-84）。
  • 原件归档：本地存储 data/originals/tenant-default/...；XML 原件必存（财会〔2025〕9 号）；S3/MinIO 存储类已实现（含 presigned_url）但未启用、零测试（storage.py:56-93）。

B. 发票解析 · 分级路由（已上线）

  • 策略链 CHAINS（parse/pipeline.py:228-233）：XML 直解（置信度 1.0）→ OFD/PDF 内嵌 XBRL 提取 → OFD 文本 / PDF 文本（pypdf）→ OCR（PaddleOCR，未部署，未装时该环节返回 None）→ VLM 多模态兜底。
  • LLM 引擎：OpenAI 兼容端点双通道（文本结构化 + VLM 看图），进程内缓存；默认关，当前 .env 已启用（DeepSeek 文本通道，VLM 留空 = 图像兜底禁用）。
  • OFD 全自研：纯 Pillow 矢量渲染（贝塞尔采样 + even-odd 填充，ofd_render.py）+ 坐标排序文本提取，摆脱了 cairocffi 系统依赖。
  • 校验：价税合计 = 不含税 + 税额、大小写金额一致、纠错字典 + 购买方抬头比对（BUYER_MISMATCH）；置信度 < 0.8 或关键字段缺失 → 人工复核。
  • 红字发票识别：关键词标记 + 转 pending_review，不自动对冲（parse/red_flag.py、workers/tasks.py:130-140）。
  • 费用归类：规则关键词优先（福利>差旅>招待>办公），LLM 兜底，再兜底 other。
  • XML 数字签名验签：signxml 按签名内嵌 X509 做完整性校验（xml_parser.py:14-50）；税务 CA 链验证未实现（注释明言待国税资质后补）。
  • 无外部服务时的降级是诚实的：OCR/LLM 缺失 → 降级到人工复核，不产假数据（_parse_chain_armed 保证非发票不误杀）。
架构债：LLM 文本通道当前是「直接落库」而非「建议后由规则闸门决策」——见 §四 目标解析架构 G1 缺口。

C. 验真与查重 ⚠️ 一半是模拟

  • 验真 = MockVerifyProvider，无真实国税 API 代码路径（verify/provider.py:19-22 实证复核）。按发票号码前缀规则返回 passed/failed/error（verify/mock.py:8-28）。模拟状态在三处主动披露：API 字段 verify_is_mock（schemas/invoice.py:70-73）、前端「模拟模式」橙色 tag（InvoiceDetailDrawer.vue:71）、月度健康报告正文声明（reports.py:260）。
  • 查重是真实的：(tenant_id, coalesce(code,''), number) 应用层查重 + DB 部分唯一索引双保险（verify/dedup.py、models/invoice.py:28-35），解析落库与验真两个环节拦截，重复票物理删除留审计。

D. 状态机与人工复核（已上线）

  • 12 态状态机（workflow/state.py）；复核 approve/reject、字段纠错后三态重校验 + 自动重验、拦截票人工放行（unblock）。
  • AI 复核预判（parse/ai_review.py）：四层判定（规则硬拦截 → OCR 置信度 → 规则通过 → LLM 边缘判断）；自动通过方向可配阈值（默认 0.0 = 观察期全人工），拦截方向永不自动；改判埋点 + 信任统计接口 /stats/trust。
  • 后台班表每 60s 为待复核票补生成预判（每批 ≤10）。

E. 银行回单（P0 已上线，P1 部分待办）

  • 已知未解（项目自证）：整页版面重排四轮启发式全部产生跨回单污染、已证伪禁做；替代方案「局部版面查询」尚未实现（receipt.py:469-473 仅留方向注释）。

F. 报销（已上线，入口有缺口）

三、离上线/商用还差什么（分级清单）

3.1 阻塞级——不解决不能对客收费

#差距事实依据性质
B1 验真是模拟，无真实国税 API 路径 verify/provider.py:19-22 无条件返回 Mock；FRD §7.1 验收标准「成功调用国税 API」、§4.3「验真覆盖率 100%」均为合规硬约束 外部依赖（国税资质）+ 开发（真实 provider）
B2 安全基线未达标 ① jwt_secret 默认 change-me 且本地 .env 实测仍是 change-me（token 可伪造）；② 初始管理员 admin/admin123 且 .env 未改；③ FERNET_KEY 是占位值（见 R1 后果）；④ 无登录限流/失败锁定（已明确裁决不做，商用需重新评估）；⑤ 无 CORS/TrustedHost 中间件；⑥ workbuddy_inbox_dir 空 = MCP 可读任意路径 纯开发，成本低但必须做
B3 生产部署形态不存在 无 Dockerfile/应用 compose/nginx/TLS 终结/备份恢复方案；PG/Redis/S3 全部未实测（Plan D 清单「待启动」）；SQLite→PG 已知雷：naive-UTC 时间戳会 TypeError、迁移需按 PG 重新生成核对；S3 分支零测试、无 404 守卫、整文件读内存 需有 Docker 的环境 + 开发
B4 多租户隔离是空架子 tenant_id 全硬编码 default、查询层无任何租户过滤、users/mailboxes/audit_logs 等表无租户列；数据边界实际只有「角色 + 员工本人」。若商用形态是 SaaS 必须架构级改造；若是单企业私有化则应正式裁决「不做多租户」 架构决策 + 开发
B5 运维兜底为零 无日志落盘/轮转、无 metrics、无告警（仅可选企微 webhook）、调度器与 API 同进程（单点，重启丢任务） 开发 + 运维设计

3.2 高风险——带着上线会出事故

#风险事实依据
R1 邮箱密码加密跨重启失效（实锤 bug） fetch/crypto.py:5：fernet_key 长度≠44 时每次启动随机生成新 key；当前 .env 的 FERNET_KEY 正是占位值 → 已加密落库的 IMAP/SMTP/agently 凭据重启后解密必炸，收取通道瘫痪。顺带：admin_password 改了也一样，重启后邮箱全失联
R2 zip 炸弹无防护 unpack_zip 无条目大小/数量上限，加密 ZIP 成员 zf.read RuntimeError 未兜底（Plan D 已记录）
R3 数据删除/容量类 发票删除全字段快照审计（好），但审计表无索引、无分区，量大后查询/清理会拖垮
R4 前端工程隐患 dayjs 是 antd 传递依赖（未声明，升级 antd 可能崩）；角色数组 5 处重复硬编码；401 用 window.location 硬跳丢状态
R5 legacy 全局 MCP token 兼容通道 一枚静态 token = 最小 id admin 全权，商用前应禁用通道（新部署留空即禁用的开关已有）
R6 LLM 云端 vs 离线合规矛盾 FRD 要求「支持纯离线部署，数据不出内网」；当前 .env 把发票内容发往 api.deepseek.com。机制上 OpenAI 兼容端点可换内网模型，但离线部署时必须强制配置内网 LLM 或关闭，目前无启动校验
R7 队列单进程 local 模式下解析/验真与 API 同进程；量大后阻塞请求（回单已用后台线程规避，发票仍是同步内联）

3.3 产品功能缺口（非阻塞，影响完整度）

  • OCR 未部署：图片/扫描件目前一律拒收或落人工，FRD 分级路由的第 3 级形同虚设（P0-3；需 paddleocr/pymupdf 环境 + 离线模型预置）。
  • VLM 通道未配置：模糊件兜底缺一半（MODEL_VLM 空）。
  • 回单多银行 P1：局部版面查询未实现；农/招/中模板无字段标签（等真实样本）。
  • 无票支出录入入口、发票列表导出、批量提交金蝶/用友 API、时限管理、风险标签扩展、入账标识、档案包等（项目自己的 P1–P3 排期，见《高优先级任务总表》《待办清单》）。
  • 明确不做（YAGNI，已裁决）：费控、商旅、信用抽审、银企直联/申报自动化（保持人工）、自建开票、自助注册、登录失败锁定、密码强度规则、逐人细粒度权限——商用前需重新确认这批裁决客户能否接受。

3.4 外部依赖（不是编码问题）

  1. 国税查验平台资质（B1 的前置）
  2. OCR 运行环境 + 离线模型
  3. 真机验收清单未执行（2026-08-18 定的 5 项：真实回单 PDF、企微真实推送、员工真实上传全链路、WorkBuddy 平台挂载实测、真实数电票验真回归）
  4. 观察期数据评估（B1 改判埋点自 2026-08-17 积累，决定 auto_review_threshold 是否开启）
  5. 银行对账单样本（F 组电子对账单的前置）

3.5 需要产品/商业决策的

决策点选项与影响
商用形态单企业私有化（便宜：正式放弃多租户，B4 消解大半）vs SaaS（昂贵：租户隔离架构级改造）
验真过渡口径国税资质下来之前，能否以「模拟模式显著声明 + 人工查验兜底 SOP」对外？还是必须等资质？

四、目标解析架构：OCR + 规则 + LLM + 人工

这是商用口径下的架构裁决——MVP 阶段实现的「解析 → 校验 → 复核」是骨架，本节定职责边界，把 LLM 锁死在「建议层」而非「决策层」。

层4 规则硬校验 金额自洽、税号格式、大小写一致、查重 绝对（确定性规则） 决策层 ✅ 已上线（validation / dedup / verify）
层5 交叉验证 OCR ↔ LLM 同字段结论比对，不一致转人工 — 触发人工 ❌ 未实现（VLM 是前置）
层6 人工复核 低置信、字段冲突、关键字段被 LLM 修改、高风险 绝对（人确认） 兜底 ✅ 已上线（状态机 + AI 预判）
层7 反馈闭环 人工修正结果回流：纠错字典 / LLM prompt 版本 / 模板库 — 持续改进 ⚠️ 改判埋点已上线（ai_review.py），回流管线未实现

4.3 关键原则（架构硬约束）

  1. LLM 是建议层，不是决策层
    • 关键财务字段（金额、税额、价税合计、税号、账号、发票号）→ 必须经过规则硬校验通过才能落库
    • LLM 对这些字段的修改必须标记为「suggested / 可疑」，由规则或人工最终确认
    • 非关键字段（摘要、科目、备注、政策匹配）→ LLM 建议可直接采用（可逆）
  2. 关键字段修改必须留痕
    • LLM 任何修改关键字段的建议 → 写审计表，含 prompt 版本号、输入摘要、采纳/驳回
    • 「拦截方向永不自动」已在 ai_review.py 实现（AI 只能建议放行，不能建议拦截）
  3. 多源交叉验证是兜底，不是可选项
    • OCR 与 LLM 对同一关键字段结论不一致 → 转人工，UI 高亮冲突
    • 仅 OCR 可信度 < 0.8 → 转人工（已实现）
  4. 离线部署时 LLM 必须内网化
    • FRD 要求「数据不出企业内网」；当前 .env 把发票内容发往 api.deepseek.com
    • 启动校验：OFFLINE_DEPLOY=true + 检测到云端 endpoint → 拒绝启动（当前 R6 已记录未做）
