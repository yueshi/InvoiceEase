一句话方案

Agently Mail 是「Agent 原生邮箱」，没有 IMAP/SMTP 协议，一切访问走 agently-cli 命令。 方案：把它做成发票易 MailFetcher 协议的第二个实现（AgentlyFetcher）， 收取之后的附件过滤 → 解析 → 验真 → 归档全链路零改动复用。

核心决策

决策点方案状态
防重复收取 Agently 无 \Seen/uid → last_uid 语义改为时间戳游标（ISO→unix 秒）； 主力防线是既有 (email_message_id, file_url) 唯一索引。宁重勿漏。 实测确认
去重键选择 email_message_id 用 rfc_message_id（标准 RFC 格式，与 IMAP 语义统一）； message_id（msg_ 前缀）仅作回复定位（provider_message_id）。 实测确认
取信流程 +list（分页循环 next_cursor）→ 对 has_attachments 消息 +read 取附件清单 → 逐个 +download；大附件（download_url）走 HTTP 下载分支。 实测确认
拒收回复 agently 走 +reply，两步确认：首跑拿 confirmation_token → 重跑完成； 固定模板场景优先 --confirmed 跳过（+reply 支持与否待验证）。 部分待验
认证/无头 本机 keychain 已授权；服务器部署用 AGENTLY_ACCESS_TOKEN 环境变量（Fernet 加密入库，可空=依赖本机登录态）。 部署前验证
限流配额 10 req/min · 200 req/hr · 50 封/天 → AgentlyFetcher 配额意识：单轮批上限（20 封）、 429/限流指数退避、下轮续拉，审计留痕。 设计必守

实测输出契约速查

+list（stdout 即 JSON）
  • data.data[]：message_id / created_at(ISO) / from / subject / has_attachments / is_read / snippet
  • pagination：has_more / next_cursor
+read（附件清单在此）
  • attachments[]：attachment_id / filename / content_type / size；大附件为 download_url
  • rfc_message_id ← 去重键
+download / +send / +reply
  • 下载实测字节一致 ✓
  • 两步确认：confirmation_token 重跑完成
  • +send --attachment ≤10MB/个、总额 20MB、50 个

风险与决策点

  • 限流是硬约束：带附件邮件每封需 +read + download 多次请求，忙碌收件箱一轮可撞 200/hr —— 批上限 + 退避 + 审计。
  • token 长期有效性未知：收取静默失败时审计可查；「授权过期」告警面（Web 红点）为后续增强。
  • 运行时依赖：部署机需 node + agently-cli；CLI 联网调用腾讯服务，部署文档需明示（纯离线部署场景注意）。
  • 扩展性：mailbox_type 是枚举扩展点——未来第三方邮箱（Gmail API 等）同模式接入。
