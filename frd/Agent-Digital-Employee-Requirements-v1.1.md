# AI 驱动发票报销系统——开发者与 AI Coding Agent 需求及实现约束

> **v1.1**（评审后升版；2026-10-09 修订，详见末尾"v1.0 → v1.1 修订记录"）
> 与 `InvoiceEase-frd-v0.1.txt` 配套：
> 原 FRD 定义产品能力与工作流；本文件定义「Agent 数字员工」形态的架构、硬约束与实施路线。

## 一、项目背景与目标

为10-20人规模、有中国大陆财务合规需求的小企业，构建一套**AI驱动的发票报销系统**。系统以"数字员工"形态运行，用户通过自然语言对话完成报销，AI负责非结构化输入的解析与结构化输出，传统技术负责确定性验证、裁决与执行。

**核心目标**：
- 员工用一句话+发票即可发起报销，无需填表单
- AI处理发票识别、行程重构、政策匹配等模糊任务
- 传统技术保证资金、合规、审计的绝对确定性
- 支持中国大陆增值税发票、电子发票、内部自定义票据

### 1.5 主体分层与边界（v1.1 新增；解决 A1 评审问题）

spec 用「AI / 数字员工 / Skill / MCP」等多个词但没定义边界。为消除歧义，本规范明确如下分层与边界：

| 主体 | 定义 | 写权限边界 |
|---|---|---|
| **LLM（模型层）** | 模型推理实体，自身不持任何状态 | **零写权限**。LLM 不直接访问 DB、不直接调 MCP、不写文件、不发起网络请求。LLM 的输出仅为「对话 + 工具调用声明」，必须经 MCP Server 落地。 |
| **Skill（业务编排层）** | 封装业务逻辑的指令集（一个 Skill 文件 = 一份提示词 + 编排规则） | **间接写**。Skill 本身不写；通过声明「MCP 工具调用顺序 + 入参 + 预期结果」编排动作；所有副作用必须经 MCP Server。 |
| **MCP Server（能力执行层）** | 暴露 MCP 协议 Tool 的服务进程 | **受控写**。read-only 工具按规格标注；write 工具必须经规格指定的确认通道（见 §7.5）。 |
| **数字员工（合成主体）** | 由 LLM + Skill + MCP Server + 会话历史 + 审计链组成的运行实体 | 通过 MCP 通道产生的所有副作用，审计记 `actor_type=agent`。 |
| **system cron / scheduler** | 系统级定时任务，不接受用户/Agent 触发 | 系统级写权限，受 `assert caller == "scheduler"` 护栏保护，审计记 `actor_type=system`。 |
| **Web 前端用户** | 通过浏览器登录 Web 后台的人类用户 | 视为已确认的人工通道（见 §7.5），审计记 `actor_type=user, channel=web`。 |
| **IM 用户** | 通过飞书/钉钉/企微机器人对话的人类用户 | 与 Agent 协作，所有写需经 §7.5 的 confirm 流程，审计记 `actor_type=user, channel=im`。 |

**关键不变量**：
- LLM 永远不能成为 schema 层的唯一决策者；任何副作用必须经 MCP Server
- Skill 永远不能 import DB session / 直接写模型
- system cron 是「白名单自动化」，所有白名单外的能力仍走 MCP

## 二、核心设计原则（必须遵守）

### 原则1：AI是传感器，不是决策者
AI只负责将混乱的人类输入转化为干净的结构化数据，**永远不能直接触发副作用**（付款、入账、审批通过、状态变更）。

### 原则2：确定性校验不可绕过
无论AI置信度多高，勾稽校验、查重、真伪查验、预算查询、Schema校验**必须执行**。任何FAIL直接驳回，不进入AI建议环节。

### 原则3：AI只读不写
AI不能直接修改数据库、不能直接调用付款接口、不能直接改变审批状态。AI只能调用受控的MCP工具，且写操作必须经过人工确认。

### 原则4：人工闸门内建
涉及资金流出、责任承担、规则变更、不确定性的节点，必须强制转人工。人工干预点必须在界面中高亮可见。

### 原则5：全链路审计
AI的输入、输出、Prompt、模型版本；规则引擎的决策依据；人工的操作记录——全部写入append-only日志，不可篡改。

### 原则6：幂等性与可重放
所有写操作必须幂等。同一张发票重复提交，查重层拦截；同一笔付款重复触发，幂等键阻止。整个流程可重放，用于审计和调试。

### 原则7：降级策略
AI不可用时（API故障、超时），自动降级到纯人工流程，不阻塞业务。AI是增强，不是单点依赖。

### 2.x 术语定义（v1.1 新增；解决 A2 评审问题）

为消除 §7「AI 不得直接改变审批状态」等约束的歧义，本规范明确如下术语：

- **审批状态（approval status）**：仅指 `ExpenseClaim.status` 字段的有限状态机——`draft → submitted → approved → rejected → paid`，以及其反向状态转移。其他字段变化（如 `submitted_at` 写入、`expense_type` 分类、`red_flag` 标记、`ai_review_verdict` 预判、`invoice.status` 推进）**均不属于「审批状态」变更**，各自受对应约束（见 §7.1 ❌1、§7.4 auto_review 豁免）。
- **副作用（side effect）**：任何使系统持久状态发生改变的操作，包括但不限于：DB 写入、文件落盘、外部 API 副作用调用、状态机推进、消息推送。仅返回结构化数据的纯读取/计算不视为副作用。
- **写工具（write tool）**：MCP 工具中产生副作用的子集，与"read-only tool"严格二分（详见 §7.2 ✅6 + §7.5 通道分层）。
- **确认（confirm）**：指 §7.5 规定的两段握手协议中的第二步，由人工显式提供 `confirm_token` + `human_ack=true` 才落库。
- **一次性票据（one-time ticket）**：指 `web_links.ticket` JWT，详见既有 `web_links.py` 实现。

## 四、功能模块与自动化边界

### 4.1 完全固化（AI+规则自动执行，零人工干预）

以下环节可打包为自动流水线，从发票进入系统到生成待审批报销单，全程无需人工：

| 环节 | 实现要求 |
| :--- | :--- |
| 发票文件接收与存储 | 幂等文件操作，生成唯一ID |
| 发票OCR字段提取 | 输出严格Schema JSON，低置信度转人工 |
| 发票真伪查验 | 调用税务权威接口，返回确定结果 |
| 发票查重 | 数据库唯一约束（票号+金额+供应商） |
| 勾稽校验 | 价税合计=金额+税额，容差0.01 |
| 预算余额查询 | 数据库只读查询 |
| 审批路由计算 | 规则引擎执行预定义规则 |
| 状态机流转 | 确定性代码，状态转换有明确定义 |
| 审计日志写入 | append-only，只增不改 |
| 通知发送 | 幂等操作，可重发 |

### 4.2 条件固化（满足预设条件时自动，否则转人工）

| 环节 | 自动条件 | 转人工条件 |
| :--- | :--- | :--- |
| 发票OCR提取 | 置信度≥0.95且Schema通过 | 置信度<0.95或关键字段缺失 |
| 行程重构 | 时间线完整无矛盾 | 有去程无返程、住宿晚数不匹配 |
| 政策匹配 | 精确匹配唯一政策条款 | 匹配多条或存在歧义 |
| 金额阈值判断 | 明确低于或高于阈值 | 处于阈值边界（如500元标准，实际498元） |
| 超标处理 | 超标金额<容忍值（如50元） | 超标金额≥容忍值或多次超标 |
| 异常检测 | 无异常标记 | AI标记异常或规则引擎标记异常 |
| 供应商黑白名单 | 供应商在名单中且状态明确 | 供应商不在名单中或状态模糊 |

### 4.3 必须人工（v1.1 重写；解决 B1 评审问题）

v1.0 列表按「岗位」分类，与 §4.4「按条件」分类无覆盖关系。v1.1 改为**统一按触发条件**分类，岗位授权放到 §4.5 角色矩阵：

| 触发条件 | 触发场景 | 授权岗位（默认） | 可配置项 |
|---|---|---|---|
| **资金流出节点** | 任何直接或间接触发付款的操作 | 财务主管 + 双人复核 | — |
| **责任承担节点** | 审批、特批、申诉裁决 | 当前环节审批人 + 上级 | — |
| **规则变更节点** | 报销政策、审批规则、阈值配置的变更 | 系统管理员 + 财务主管 | — |
| **异常不可判定节点** | AI 置信度低、规则冲突、信息缺失、逻辑矛盾 | 当前环节审批人 | `low_confidence_threshold` |
| **金额阈值节点** | 单笔 ≥ `large_amount_threshold`（默认 5000 元）或单笔异常超 `over_threshold_tolerance` | 当前环节审批人 | `large_amount_threshold`、`over_threshold_tolerance` |
| **合规高风险节点** | 供应商新增、银行卡号变更、跨境支付 | 财务主管 | — |

### 4.4 自动化决策清单

以下环节**在条件满足时自动执行**，无需人工；任一条件失败则降级到 §4.3 对应触发条件：

| 环节 | 自动条件 | 失败时落入 §4.3 |
|---|---|---|
| 发票 OCR 提取 | 置信度 ≥ `ocr_confidence_threshold` 且 Schema 通过 | 异常不可判定 |
| 行程重构 | 时间线完整无矛盾 | 异常不可判定 |
| 政策匹配 | 精确匹配唯一条款 | 异常不可判定 |
| 金额阈值判断 | 明确低于/高于 `large_amount_threshold` 边界 | 金额阈值 |
| 超标容忍 | 超标金额 ≤ `over_threshold_tolerance` | 金额阈值 |
| 供应商黑白名单 | 供应商在名单中且状态明确 | 合规高风险 |
| 状态机自动推进 | `auto_review_predictions` 在 `auto_review_enabled=true` 且 confidence ≥ `low_invoice_review_threshold` | 异常不可判定 |

### 4.5 角色授权矩阵（v1.1 新增）

| 角色 | 可授权操作 |
|---|---|
| 普通员工 | 发起报销（draft → submitted）、补充材料、申诉 |
| 财务专员 | submitted → approved（< 5000）、发票审核、退回补充 |
| 财务主管 | submitted → approved/rejected（任意金额）、付款授权、规则变更复核 |
| 系统管理员 | 阈值/规则配置、用户/角色管理、审计查阅 |

## 五、技术分工：传统系统 / MCP Server / Agent Skill

### 5.1 传统系统：确定性底座（全部保留，AI不可直接操作）

- 数据库与事务：报销单持久化、事务一致性、幂等控制
- 状态机：报销单生命周期管理（草稿→提交→审批→付款）
- 权限体系：RBAC角色控制、数据隔离
- 审计日志：append-only日志，记录所有操作
- 勾稽校验：价税合计=金额+税额等数学恒等式
- 查重引擎：票号+金额+供应商去重
- 预算查询：预算余额确定性查询
- 付款执行：资金操作，双人复核
- 报表导出：Excel/PDF生成

### 5.2 MCP Server：能力执行层

以下能力必须封装为MCP Server，遵循单一职责原则，分离读操作与写操作：

| MCP Server | 暴露的工具 | 读写属性 |
| :--- | :--- | :--- |
| 发票管理MCP | `search_invoices(email, date_range)`、`extract_invoice(file_id)`、`get_invoice_detail(invoice_id)` | 只读 |
| 报销系统MCP | `create_expense_report(data)`、`get_report_status(report_id)`、`update_report(report_id, patch)` | 写操作需人工确认 |
| 验证服务MCP | `validate_expense(report_id)`、`check_duplicate(invoice_data)`、`verify_invoice(invoice_no)` | 只读 |
| 审批路由MCP | `route_approval(report_id, rules)`、`get_approval_status(report_id)` | 写操作需规则引擎执行 |
| 预算服务MCP | `query_budget(dept, category, period)`、`check_budget_available(dept, amount)` | 只读 |

**MCP设计约束**：
- 每个工具必须有明确的输入Schema和输出Schema
- 写操作必须支持幂等键
- 工具返回结构化结果 + 自然语言摘要
- 所有调用记录审计日志

### 5.3 Agent Skill：业务编排层

Skill封装业务逻辑，含流程、异常处理与复用能力。采用渐进式披露，启动时每个Skill只消耗约100个token用于广告，实际使用时才加载完整指令。

| Skill名称 | 触发场景 | 编排的MCP工具 | 业务逻辑 |
| :--- | :--- | :--- | :--- |
| 差旅报销Skill | 用户说"出差报销" | 发票管理MCP + 报销系统MCP + 验证服务MCP | 行程重构、住宿/交通/餐饮标准匹配、缺失检测 |
| 餐饮报销Skill | 用户说"吃饭报销" | 发票管理MCP + 报销系统MCP | 餐补标准匹配、人均限额校验 |
| 交通报销Skill | 用户说"打车/高铁报销" | 发票管理MCP + 报销系统MCP | 起终点校验、里程合理性检查 |
| 发票补录Skill | 用户说"补充发票" | 发票管理MCP | 识别新上传发票，关联到已有报销单 |
| 超标处理Skill | 验证层返回超标标记 | 审批路由MCP + 报销系统MCP | 生成超标说明模板、路由到加签审批人 |

**Skill设计约束**：
- 遵循SOLID原则，复杂Skill委托给子Skill
- 每个Skill独立版本化
- Skill不能直接调用传统系统，必须通过MCP工具
- Skill的决策必须附依据（引用政策条款）

## 六、界面设计原则与实现建议

### 6.1 核心设计原则

1. **AI是隐形后台，界面是显性前台**：用户不应感受到AI的存在，AI只在需要确认或补充时现身。
2. **对话式交互 + 结构化确认双模式并存**：移动端对话式，PC端结构化表单，共享同一数据模型。
3. **状态可见、证据可溯、操作可逆**：每个报销单清晰展示状态，附有明确"下一步动作"标签。
4. **渐进式披露**：默认只展示核心字段，异常标记或超标项才展开详细说明。
5. **人工干预点高亮可见**：强制人工节点醒目呈现，提供明确批准/驳回按钮。

### 6.2 功能界面分工

| 界面模块 | 技术实现 | AI增强点 |
| :--- | :--- | :--- |
| 报销单列表 | 传统系统 | AI自动标注"异常待处理"标签 |
| 审批工作台 | 传统系统 | AI生成审批建议+依据摘要 |
| 财务审核台 | 传统系统 | AI高亮超标项、缺失项 |
| 报表与台账 | 传统系统 | AI自动生成费用分析摘要 |
| 权限与配置 | 传统系统 | 无 |
| 报销发起对话 | AI对话界面 | 自然语言描述，上传发票 |
| 发票上传与识别 | AI对话界面 | 拍照/转发/邮箱同步，AI返回识别摘要 |
| 多轮信息补齐 | AI对话界面 | 每轮只问1-2个问题 |
| 报销单预览确认 | AI对话界面 | 卡片展示摘要+明细展开 |
| 异常提示与处理 | AI对话界面 | AI解释原因+给出选项 |

### 6.3 关键交互流程

**对话式报销发起**：
1. 用户："上周去上海出差3天，帮我报销一下"
2. AI解析意图，追问具体日期和发票位置
3. 用户补充，AI调用MCP搜索发票、提取字段、重构行程
4. AI发现缺失（返程票）或超标（住宿），主动提示
5. 用户确认或补充，AI生成结构化报销单
6. AI展示摘要，用户确认后调用`create_expense_report`
7. 规则引擎路由审批，人工审批节点高亮

**审批界面**：
- 只展示最需要的字段：申请人、金额、AI建议、依据摘要
- 超阈值或低置信度项自动标记"需人工判断"
- 提供批准/驳回/需复核按钮

**异常处理界面**：
- 醒目展示异常类型和原因
- 提供处理选项（补充材料/申请特批/修改金额）
- 记录用户决策到审计日志

## 七、关键约束（硬性，AI Coding Agent必须遵守）

### 7.1 禁止行为
- ❌ AI不得直接操作数据库
- ❌ AI不得直接触发付款
- ❌ AI不得直接改变审批状态
- ❌ AI不得绕过`validate_expense`接口
- ❌ AI不得修改规则引擎的规则
- ❌ AI不得在`validate_expense`返回FAIL时强行提交
- ❌ AI不得在无人工确认的情况下执行写操作

### 7.2 必须行为
- ✅ 所有AI输出必须经过Schema校验
- ✅ 所有写操作必须幂等
- ✅ 所有决策必须记录审计日志
- ✅ 所有人工干预必须留痕（谁、何时、为什么、结果）
- ✅ 所有阈值和条件必须可配置，不得硬编码在Prompt中
- ✅ 所有MCP工具必须分离读写，写操作需人工确认
- ✅ 所有Skill必须通过MCP工具访问传统系统

### 7.3 性能与可靠性
- 降级策略：AI不可用时自动降级到纯人工流程
- 幂等性：同一发票重复提交，查重层拦截
- 可重放：整个流程可重放，用于审计和调试
- 低置信度处理：AI置信度<阈值时强制转人工

### 7.4 auto_review_predictions 豁免条款（v1.1 新增；解决 C1 评审问题）

§4.1 表「完全固化」列出了「AI 复核自动通过 → 状态机流转」看似违反 §7.1 ❌1 与 ❌3。本节明确豁免：

- **白名单自动**：仅当 `auto_review_predictions` 由 `system cron / scheduler` 进程触发、且 `auto_review_enabled=true`（默认 `false`，必须 admin 手动开启）、且 `ai_review_confidence ≥ low_invoice_review_threshold`（默认 0.95）时，可对 `Invoice.status` 执行 `pending_review → pending_submit` 的状态推进。
- **代码层护栏**：`parse/ai_review.py:auto_review_predictions()` 入口必须有 `assert caller == "scheduler"` 护栏，禁止被任何 MCP / Agent / Web 路径调用。
- **审计强制**：每次自动推进必须写审计：`actor_type=system, action=AUTO_REVIEW_PROMOTE, detail={threshold, confidence, reason}`。
- **UI 标记**：自动通过的发票必须在 Web 列表 + 详情页显著标记「数字员工自动通过（阈值 X）」，鼠标悬停展示 AI verdict 与 confidence；财务复核时必须能识别哪些是 AI 推过去的。
- **回滚通道**：财务专员/主管可一键把自动通过的发票退回 `pending_review`，回滚动作写 `actor_type=user`。

除上述白名单外，§7.1 ❌1/❌3 严格生效：任何其他场景下 LLM / Skill / Agent 不得推进审批状态。

### 7.5 通道分层与两段握手（v1.1 新增；解决 C2 评审问题）

本规范区分三种写入口通道，对应不同的"人工确认"语义：

| 通道 | 入口 | 主体类型 | 是否需两段握手 | 审计 actor_type |
|---|---|---|---|---|
| **Web 人工通道** | 浏览器登录 Web 后台、调用 REST API | 已登录人类用户 | **否**（登录态即为已确认） | `user, channel=web` |
| **MCP Agent 通道** | WorkBuddy/Claude/Cursor 等 Agent 通过 MCP 调工具 | Agent（合成主体） | **是**（除纯读工具外，写工具均需 `confirm_execute(proposal_token, human_ack=true)`） | `agent, channel=mcp` |
| **IM 通道** | 飞书/钉钉/企微机器人接收用户消息 | Agent + IM 用户 | **是**（同 MCP 通道；额外在 IM 端展示 confirm 卡片，用户点确认后回调） | `agent, channel=im` |
| **System 通道** | cron / scheduler / 内部事件总线 | 系统进程 | 仅白名单自动任务（参见 §7.4） | `system, channel=scheduler` |

**两段握手协议**（仅适用于 MCP/IM 通道）：

```
Step 1: Agent 调 *_proposal(...) → 返回 proposal_token（不落库）
Step 2: 人类用户在 Web 或 IM 端 review 提案卡片
Step 3: 人类提供 confirm_execute(proposal_token, human_ack=true) → 服务端校验 + 落库 + 写审计
```

- `proposal_token` TTL 默认 15 分钟，仅可消费一次；超时失效
- 所有 `*_proposal` 工具的入参必须含 `idempotency_key: str | None`，服务端以 (idempotency_key, tool_name) 为唯一键，重复调用返回缓存结果不重复执行
- `confirm_execute` 必须校验 `human_ack=true`，缺失视为未确认直接 400
- 同一工具的 `*_proposal` 与 `confirm_execute` 在 MCP server 层为白名单枚举；未声明的工具名直接 403

**豁免**：
- 以下写工具因风险等级低、不涉及资金/状态/合规，**不要求两段握手**（但仍需 `idempotency_key` + audit）：`invoice_classify`、`receipt_pair`、`company_info_save`、`bank_account_save`（涉及账号变更需二次确认，参见 §7.5.1）
- 用户主动在 Agent 对话中显式说"我已确认/请执行"并附 `human_ack=true` 时，可省略 Step 2 的 IM 卡片确认；服务端仍必须校验 `human_ack=true` 字段

#### 7.5.1 高风险子项（v1.1 新增）

下列写操作即使在 Web 通道也要求二次确认（前端弹确认 modal）：
- `bank_account_save` / `bank_account_delete`：账号变更
- `invoice_unblock`：拦截放行
- `policy_rule_update`：规则变更（仅 admin）
- 大额报销（`amount ≥ large_amount_threshold`）的 submit/approve

Web 通道的二次确认走前端 modal，**不**走 §7.5 的 proposal_token 协议（避免双重确认）。

## 九、中国大陆财务合规特别要求

- 支持增值税发票（专票/普票）、电子发票（PDF/OFD/XML）
- 集成税务发票云进行真伪查验
- 支持中国会计准则（PRC GAAP）
- 如需完整财务合规，可评估ERPNext中国版或专用发票工具（如InvoiceDock）
- 所有财务数据存储在中国大陆境内服务器

### 9.5 数据分级与隐私（v1.1 新增；解决 F1 评审问题）

依据《个人信息保护法》(PIPL) 与等保 2.0 三级要求，本节明确数据分级与处理约束：

#### 9.5.1 数据分级

| 级别 | 字段示例 | 加密要求 | 保留期 | 访问审计 |
|---|---|---|---|---|
| **L4 绝密** | 银行卡号、CVV、支付密码 | 字段级 AES-256 + 传输 TLS 1.3 | 业务结束后 24 小时内 token 化，原始值立即丢弃 | 每次读写 |
| **L3 敏感** | 发票号码、价税合计、报销人身份证号、税号、银行账号 | 字段级 AES-256 + 传输 TLS 1.3 | 财务保留期 10 年 | 每次读写 |
| **L2 内部** | 报销人姓名、部门、报销事由、审批意见 | 传输 TLS 1.3（存储可明文） | 财务保留期 10 年 | 每次读写 |
| **L1 公开** | 公司组织架构、政策文档、聚合统计 | 无 | 永久 | 抽样审计 |

#### 9.5.2 用户权利（PIPL 第四章）

- **知情权**：所有用户提交发票/报销时，前端必须展示简明告知书，列明字段用途、共享范围、保留期
- **决定权**：用户可拒绝非必填字段，必填字段需标注"如不提供将无法使用 XX 功能"
- **查询/复制权**：用户在 Web 个人中心可一键导出本人的全部 L3/L4 数据
- **删除权**：用户撤回本人 L2/L3 数据时，DB 软删除 + 90 天后物理删除；但财务凭证类 L3 数据（发票、报销单）按 §9.5.1 保留期 10 年不可删
- **自动化决策说明**：「数字员工自动通过」必须可解释（参见 §7.4 UI 标记）；用户对自动化决策不服可走 §4.3 责任承担节点申诉

#### 9.5.3 审计增强（与 §7.2 ✅3 配套）

`AuditLog` 必含字段：
- `id`、`actor_type ∈ {user, agent, system}`、`actor_id`、`channel ∈ {web, mcp, im, scheduler}`
- `action`、`target_type`、`target_id`、`outcome ∈ {success, blocked, failed, error}`
- `llm_call_id`（Agent 触发的记录）、`prompt_hash`（Agent prompt SHA256）、`model_version`
- `detail` JSON（含 reason / before / after 状态快照）、`ip_address`、`created_at`

模型版本变更（`model_version` 切换）必须写 `MODEL_CHANGED` 审计，便于追溯不同模型版本的决策差异。

### 9.6 部署环境与地域约束（v1.1 新增；解决 F3 评审问题）

| 部署档位 | 数据库 | 对象存储 | 地域约束 | 用途 |
|---|---|---|---|---|
| **开发态** | SQLite（本地文件） | 本地 MinIO（dev） | 无（境外机器亦可） | 工程师本地开发 |
| **测试态** | PostgreSQL（内网部署） | 内网 MinIO | **限中国大陆境内** | CI/CD 集成测试、客户验收测试 |
| **生产态** | PostgreSQL（高可用） | 阿里云 OSS / 腾讯云 COS | **必须中国大陆境内**（阿里云华东/华北、华北2 等） | 客户生产 |

#### 9.6.1 多租户隔离（生产态必选）

- 物理隔离：每个 tenant 独立 DB schema，跨 schema 查询需 `tenant_id` 显式 JOIN
- 逻辑隔离：所有表带 `tenant_id` 列；ORM 层强制 WHERE 注入
- 跨租户操作：仅 `system` actor 可执行，写 `CROSS_TENANT_OP` 审计

#### 9.6.2 跨境约束

- 所有 L3/L4 数据不得离开中国大陆境内
- LLM 调用必须使用中国大陆境内端点（阿里云通义、腾讯混元、智谱、月之暗面 Kimi 等）；不可使用境外端点（OpenAI/Anthropic/Google 等）
- LLM 端点配置走 `settings.llm_endpoint_*` 列表，CI 检查端点域名后缀必须为 `.cn` 或境内云厂商内网域名

## 十、附录：术语与参考

- **MCP**：Model Context Protocol，标准化连接协议，让AI安全触达现实世界的数据与工具
- **Skill**：封装业务逻辑的"经验包"，含流程、异常处理与复用能力
- **渐进式披露**：先展示精简元数据，调用时再加载完整指令，节省上下文消耗
- **HITL**：Human-in-the-Loop，人工在环，关键决策由人确认
- **幂等性**：同一操作重复执行结果一致，用于防止重复付款/重复创建
